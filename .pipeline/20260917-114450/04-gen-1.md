## 이슈 / 결정사항

### 1. TypeScript 를 7.0.2 → 6.0.3 으로 내렸다 ★

**데코레이터는 문제가 아니었다.** TS 7.0.2 에서 `emitDecoratorMetadata` 가 정상 emit 되고
(`__metadata("design:paramtypes", [DepService])` 확인), NestJS 12 DI 가 런타임에 해석되며,
TypeORM 1.1.1 엔티티 메타데이터도 정상 등록된다. **원래 "미확인"이던 리스크 3건은 모두 해소됐다.**

막은 것은 린터다. TS 7 은 Go 네이티브 포트라 **JS 컴파일러 API 를 배포하지 않는다**
(`typescript` 패키지 `exports` 가 `./lib/version.cjs` 하나뿐). 그래서:

```
Error: typescript-eslint does not support TS 7.0.
```

경고가 아니라 **프로세스가 죽는 하드 에러**다. 안정 버전 중 TS 7 을 지원하는 typescript-eslint 는
없고(peer: `>=4.8.4 <6.1.0`), 02-context 가 oxlint 를 명시적으로 기각했으므로 린트 포기도 불가능하다.

`typescript@6.0.3` 은 **JS API 를 가진 마지막 릴리스**라 딱 한 단계만 내리면 된다.
TS 6.0.3 으로 스파이크 전체를 재실행해 동일하게 통과시켰고 ESLint 도 exit 0 이다.

**TS 7 병행 설치(`tsgo@npm:typescript@7.0.2` 별칭)도 동작을 확인했으나 채택하지 않았다** —
컴파일러가 둘이면 타입 에러 판정 주체가 둘이 되고 IDE(6)와 CI(7)가 불일치한다.

**재승급 조건**: typescript-eslint 가 TS 7 지원을 정식 배포하면([#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940))
즉시 올린다. 바꿀 파일은 `package.json` 4곳의 핀과 tsconfig 프리셋뿐이고 **앱 코드는 무수정**이다.

### 2. NestJS 12 가 순수 ESM 이라는 것을 발견했다 (계획에 없던 제약)

Nest 11 은 dual 패키지였으나 12 는 `"type": "module"` + CJS 조건 없음이다.
CommonJS 로 두면 전 파일이 TS1479 로 깨진다. 위 "전달할 사항 2번"이 그 귀결이다.
**이건 버전 선택 문제가 아니라 아키텍처 제약**이라 별도로 강조해 둔다.

### 3. ioredis 6 peer 경고는 수용했다 (하향 안 함)

```
YN0060: ioredis 6.0.0 doesn't satisfy what typeorm requests (^5.0.4)
```

TypeORM 의 ioredis peer 는 **optional 이고 Redis 쿼리 캐시 전용**이다. 우리는 안 쓴다.
**BullMQ 6.3.6 은 `ioredis: >=5.0.0` 을 명시 지원**하므로 6 은 정식 범위다.
`logFilters` 로 지우는 것도 시도했으나 glob 이 매칭되지 않았고, 억지로 넓히면 **다른 peer 경고까지
가릴 위험**이 있어 **경고를 그대로 두고 `.yarnrc.yml`·README 에 설명을 남기는 쪽**을 택했다.

### 4. yarn 4.18 의 24시간 공급망 검역을 끄지 않았다

`npmMinimalAgeGate: 1440` 기본값이 배포 24시간 미만 패키지를 거부한다.
prettier 3.9.7 과 @tanstack/react-query 5.103.1 이 걸렸다(둘 다 2026-09-16 배포).
**보안 장치이고 CLAUDE.md 보안 수칙에 부합**하므로 끄지 않고 직전 안정 버전으로 핀했다.
24시간 후 언제든 올릴 수 있다(기능 차이 없음).

### 5. ⚠️ docker-compose 가 회사 DB 비밀번호를 빨아들이는 것을 발견해 차단했다

최초 작성본은 02-context 파일 목록대로 `${DB_PW}` 를 썼다. 그런데 `docker compose config` 출력에
**개발자 셸에 export 돼 있던 회사 공용 `DB_PW` 실값이 그대로 찍혔다.** compose 는 ambient 환경변수를
`.env` 보다 우선하기 때문이다. 그대로 뒀다면 로컬 MySQL 컨테이너가 **회사 운영 비밀번호를 root 암호로**
들고 떴을 것이고, 더 나쁘게는 앱이 같은 `DB_HOST`/`DB_PW` 를 읽어 **회사 DB 를 가리킬 수도** 있었다.

→ compose 전용 변수를 **`TESTFLOW_` 접두사로 분리**하고 기본값을 로컬 더미(`testflow_local`)로 고정했다.
`.env.example` 에도 "앱이 접속할 주소(`DB_*`)"와 "컨테이너를 띄울 값(`TESTFLOW_*`)"을 구분해 적었다.
**Gen-Phase 4 에서 `ConfigModule` 을 붙일 때도 같은 함정이 있다** — `process.env` 가 회사 값으로
오염돼 있을 수 있으니 `.env` 파일 우선 로딩 여부를 명시적으로 결정할 것.

### 6. 포트 3306 이 이미 사용 중이라 기본값을 3307 로 바꿨다

`websystem-mysql` 컨테이너가 3306 을 점유하고 있었다. 같은 개발 머신에서 공존해야 하므로
TestFlow MySQL 기본 포트를 **3307** 로 정했다(`docker-compose.yml` 기본값 + `.env.example` 의
`DB_PORT`/`TESTFLOW_DB_PORT` 모두 3307). Redis 6379 는 비어 있어 그대로 뒀다.

### 7. 계획서의 vitest·ESLint 버전이 옛 정보였다

03-phases/02-context 는 vitest 3.x, ESLint 9 로 적혀 있으나 실제 최신 안정은 **vitest 5.0.1, ESLint 10.10.0** 이다.
