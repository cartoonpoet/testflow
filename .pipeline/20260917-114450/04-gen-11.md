## ★ SSE 실시간 반영 실측

**진짜로 받았다.** MySQL(3307) + Redis + API(4000) + **Runner** + 웹(`vite preview` 4173) 을
전부 띄우고, Playwright 로 실브라우저에서 `RunDialog` → 실행 → 실행 현황 화면을 열어
**스텝이 하나씩 바뀌는 것을 250ms 간격으로 폴링해 기록**했다.
대상은 Gen-Phase 7 의 `apps/runner/poc/fixtures/record-login.html`(무수정, `python3 -m http.server 5301`).
`lib/sse.ts` 가 **여기서 처음 실전 검증됐다**(04-gen-8·9 가 미검증으로 남긴 항목).

### 스텝별 상태 전이 (8스텝 시나리오, `wait 3000` 3개 포함)

```
#1 passed | #2 passed | #3 running→passed | #4 pending→passed
#5 pending→running→passed | #6 pending→passed | #7 pending→running→passed | #8 pending→passed
```

폴링 간격(250ms)보다 짧게 끝난 스텝(14~49ms)은 `running` 프레임을 못 잡았을 뿐이고,
**3초짜리 `wait` 스텝은 전부 `pending → running → passed` 3단계가 관측됐다.**

### 중간 상태 스크린샷 — `/tmp/tf11/02-run-midstate.png`

```
rows = passed,passed,running,pending,pending,pending,pending,pending
progress = "3 / 8 단계"   spinner(DOM) = true   pulse(DOM) = true
```

완료 `✓` · 실행 중 **회전 스피너** · 대기 **숫자**가 한 화면에 동시에 보인다(육안 확인함).
요약바의 `N / M 단계`가 스텝 진행에 맞춰 갱신되고, 종료되면 `pulse` 점이 사라진다(`pulse=false`).

## ★ Last-Event-ID 재연결 실측

### 먼저 실패한 시도 (사실 기록)

**`context.setOffline(true)` 는 이미 열린 EventSource 를 끊지 못한다.** 6초 차단하는 동안
`connection=open` 이 유지되고 수신 계수가 6→14 로 계속 늘었다. "끊었다고 생각했는데 안 끊긴"
상태로 통과 판정을 냈다면 거짓 보고가 될 뻔했다. 그래서 **웹을 서빙하는 `vite preview` 프로세스를
실제로 죽이는** 방식으로 바꿨다(죽은 직후 `curl` 응답 코드가 `000` 인 것을 확인하고 진행).

### 진짜로 끊고 다시 붙인 결과

```

[cut]       차단 중 connection=reconnecting  received=6 (멈춤)  재시도 배너=표시됨

            /api/runs/<id>/events
```

### batch 결과를 어떻게 보여주는가

스위트 실행은 **`batch_id` 로 묶인 run N건**이 생긴다. 그런데 목록 응답(`RunListItem`)에
`batchId` 가 **없어서** 서버에 "이 묶음만" 을 물어볼 수 없다(계약에 필드를 추가하면 API 도
고쳐야 하는데 이번 범위 밖이다). → `RunDialog` 가 202 응답의 `runIds` 를
**`/runs?batch=<batchId>&ids=id1,id2,id3`** 로 넘기고, `/runs` 화면이 그 id 로 각각 상세를 읽어
**묶음 패널**을 맨 위에 그린다.

```
[batch] batchId=c35ccc9c-…  runIds=3건
[batch] 화면 묶음 행 3건 → 최종 passed , passed , passed
[batch] 서버 확인 — run 3건의 batch_id 종류=1 (전부 같은 값)
[batch] 시나리오 순서 = 묶음 시나리오 1 → 묶음 시나리오 3 → 묶음 시나리오 2   ← ▲ 로 바꾼 순서 그대로
```

묶음 행은 **SSE 가 아니라 2초 폴링**이다(종료되면 멈춘다). 행마다 EventSource 를 열면
HTTP/1.1 의 오리진당 동시 연결 6개를 바로 먹는다. 실시간 반영은 상세 화면이 한다.

   지우면 시안과 같아지지만, **가짜 로그인 화면을 실제 화면으로 오해하는 쪽이 더 위험해서 남겼다.**
2. **`skipped` 상태를 새로 그렸다.** 시안은 3-상태만 준다. 대기와 같은 중립색 + `–` 글리프를 썼다
   (빨간색으로 그리면 취소된 실행이 "전부 실패" 로 보인다).
3. **요약바 문구를 상태에 맞춰 바꾼다.** 시안은 "스테이징 환경에서 실행 중" 고정이다.
   `대기 중` / `실행 중` / `실행 성공·실패·취소됨` / `— 취소 중` 으로 갈린다.
4. **`queued` 큐 위치(`position`)를 표시하지 못했다.** `RunDetail` 계약에 그 필드가 없다
   (`CreateRunResponse` 에만 있고 새로고침하면 사라진다). 대신 "Runner 가 큐에서 가져가면
   자동으로 시작됩니다" 안내를 띄운다. — **미충족 항목으로 남긴다**(Task 11.6 작업 설명의 일부).
5. **`/runs` 목록·스위트 화면은 시안에 없다.** 위 "스위트 화면 설계" 표대로 기존 패턴만 재사용했다.

## 이슈 / 결정사항

### 1. ★ "취소했습니다" 라고 먼저 말하지 않는다

API 응답 `{"status":"cancelled"}` 는 **요청을 접수했다는 뜻**이지 실행이 끝났다는 뜻이 아니다
(`running` 이면 Redis 채널로 신호만 간다). 화면이 그 응답으로 `cancelled` 를 그리면,
실제로는 브라우저가 아직 도는 380ms 동안 **끝났다고 거짓말**을 하고 SSE 가 오면 표시가 흔들린다.
→ 버튼 라벨과 요약바 문구만 "취소 중" 으로 바꾸고, 상태는 Runner 가 확정할 때까지 건드리지 않는다.

### 2. ★ `run.finished` 뒤 한 번 더 읽는다 (실측으로 드러난 필요)

첫 구현은 이벤트만으로 화면을 만들었다. 그 결과 취소된 실행이
`passed, skipped, **pending**` 으로 보였다 — 서버는 `passed, skipped, skipped` 다.
중단된 뒤 스텝은 `step.finished` 없이 DB 에서만 `skipped` 가 되기 때문이다.
→ `run.finished` 수신 시 상세·증적을 한 번 재조회한다. 재측정에서 `passed, skipped, skipped` 로 일치.
**이 버그는 "취소를 실제로 눌러 보지 않았으면" 절대 안 보였다.**

### 3. 빈/에러/로딩 컴포넌트를 새로 만들지 않았다

Task 11.8 은 `EmptyState.tsx` / `ErrorState.tsx` / `LoadingState.tsx` 를 지정했지만,
Gen-Phase 9 가 만든 `StateView`(tone `empty|error` + 재시도) 와 `Skeleton` 이 정확히 그 역할이고
"새로 만들지 말고 이걸 써라" 라고 인계했다. 같은 UI 를 두 벌 두면 화면마다 다른 빈 상태가 생긴다.
→ **재사용했고, 대신 화면별 스켈레톤(`RunStepListSkeleton`·`RunListSkeleton`·`SuiteTableSkeleton`)을
실제 표와 열 수·패딩이 같게** 만들었다(Gen-Phase 9 규율).

### 4. 빌더에 `▶ 실행` 버튼을 붙였다 (Gen-Phase 10 산출물 수정 1건)

`RunDialog` 를 만들어도 **여는 곳이 없으면 핵심 경로가 닫힌다.** 해피패스의 마지막 칸이
"발행 → 실행" 이므로 빌더의 `.page-head` 우측(임시 저장 / 발행 사이)에 버튼 하나를 넣었다.
스텝이 0개면 비활성 + 이유를 `title` 로 설명한다. 그 외 Gen-Phase 8·9·10 산출물은 무수정이다.

### 5. Radix `Dialog` 는 쓰고 Radix `Select` 는 안 쓴다 (판단이 다른 이유)

04-gen-8 이 Select 를 네이티브로 둔 이유는 "시안이 커스텀 드롭다운을 요구하지 않아서" 다.
다이얼로그는 반대다 — **포커스 트랩·스크롤 락·`aria-modal`·Esc** 가 필요하고, 특히
**비밀번호를 입력받는 폼**이라 포커스가 뒤 화면으로 새면 안 된다. 네이티브 `<dialog>` 는
그 처리가 브라우저마다 다르다. 새 의존성도 아니다(이미 설치된 `radix-ui` 안에 있다).
애니메이션은 넣지 않았다 — `prefers-reduced-motion` 처리가 따라붙을 이유를 만들지 않는다.

### 6. 화면에 `data-sse-*` 진단 속성을 남겼다

`data-sse-connection` · `data-sse-received` · `data-sse-duplicates` · `data-sse-last-id` ·
`data-sse-resyncs`. **재연결·중복 검증을 DOM 으로 관측하기 위한 것**이고 사용자에게 보이지 않는다.
이 속성이 없었다면 "놓친 것만 받았다" 를 증명할 방법이 스크린샷밖에 없었다. 유지 권장.

### 7. 비밀번호는 세 겹으로 막았다

① 폼: `type="password"` + 전송 후 즉시 비움 · ② 화면 전달: `maskRecord()` 사본만 `history.state` 로
· ③ 서버에서 온 값: `error_message` 는 **이미 마스킹된 것**을 그대로 쓴다(화면에서 다시 가공하지 않는다).
실측: HTML·localStorage·sessionStorage·cookie·history.state 어디에도 평문 0건.

### 8. 범위 준수

  전부 손대지 않고 위 인계 표에 적어만 뒀다.
- `apps/api` · `apps/runner` · `packages/db` · `packages/contracts` · `docker-compose.yml` 은

- 시드 데이터는 전부 **공개 API 로** 만들었다(DB 직접 INSERT 없음).
