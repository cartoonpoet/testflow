## 스트리밍 방식 결론

**1안(`page.screencast` 공식 API)을 채택했다.** 2안(CDP)도 구현해 같은 조건에서 측정했다.

| | 1안 `page.screencast` | 2안 CDP `Page.startScreencast` |
|---|---|---|
| p50 / p95 지연 | **10.2 / 18.7 ms** | 13.4 / 21.1 ms |
| fps | **59.89** | 59.53 |
| 클라 드롭 | 0 | 2 |
| ack 관리 | 불필요 | `screencastFrameAck` 필수 (안 보내면 프레임이 멈춘다) |
| `pageScaleFactor` | 보조 CDP 세션 필요 | 프레임 metadata 에 포함 |

- **1안이 근소하게 빠르다.** ack 왕복이 한 번 없기 때문으로 보인다.
- `size: {1280, 800}` 을 **명시**했다. 미지정 시 800×800 으로 축소돼 좌표 변환이 깨진다(02-context).
- `pageScaleFactor` 는 1안에서도 필요해, `trackPageScale: true` 로 **보조 CDP 세션**을 붙여
  `Page.getLayoutMetrics` 로 읽는다. 이번 대상들에서는 전부 **1.000** 이었다(보정이 발동한 적 없음).
- **2안으로 내려가도 `onFrame` 시그니처는 변하지 않는다.** `StartScreencast` 타입 별칭으로
  고정했고, 전환은 `TESTFLOW_SCREENCAST_DRIVER=cdp` 또는 `startScreencast(page, {driver:'cdp'})` 뿐이다.
  실제로 measure.ts 가 같은 코드로 두 드라이버를 모두 돌려 위 표를 만들었다 — **전환 가능성이 측정으로 증명됐다.**

## 입력 역주입 방식 비교 결과

같은 27 케이스를 두 경로로 각각 돌렸다.

| | CDP `Input.dispatchMouseEvent` | Playwright `page.mouse.*` |
|---|---|---|
| 적중률 | **27/27 (100%)** | **27/27 (100%)** |
| 최대 좌표 오차 | 0.00 px | 0.00 px |

**정확도는 완전 동률이다.** 02-context 의 "CDP 가 더 직접적" 가설은 *정확도 면에서는* 성립하지 않았다.
그래서 다른 축으로 갈랐고, **CDP `Input.*` 을 채택**한다. 근거 3가지 —

1. **`down`/`up` 의 의미가 더 곧다.** Playwright 의 `mouse.down()/up()` 은 "현재 커서 위치"에 찍히므로
   좌표를 쓰려면 매번 `mouse.move()` 를 선행해야 한다(코드에 그렇게 되어 있다). 원격 조작은 좌표가
   1급 정보인데, 상태(커서 위치)를 경유하면 이벤트 순서가 뒤집혔을 때 조용히 엉뚱한 곳을 누른다.
2. **IME 가 어차피 CDP 를 요구한다.** `Input.insertText` / `imeSetComposition` 에 대응하는 Playwright
   API 가 없다. 드라이버를 Playwright 로 두면 마우스는 Playwright, IME 는 CDP 로 **경로가 두 개**가 된다.
3. **키 이벤트 제어폭.** `dispatchKeyEvent` 는 `rawKeyDown`/`keyDown`/`char` 를 구분해 보낼 수 있어
   "조합 없는 입력은 키 이벤트로, 한글은 `insertText` 로" 가르는 02-context 권고를 그대로 구현할 수 있다.

**Playwright 경로는 삭제하지 않고 남겼다.** 같은 인터페이스 뒤에 있고
`TESTFLOW_INPUT_DRIVER=playwright` 로 전환된다. CDP 쪽에서 원인 불명의 문제가 생겼을 때
**대조군으로 쓸 수 있다는 것이 이번 측정의 실질적 수확**이다(정확도가 같으니 진짜 대조군이 된다).

## 이슈 / 결정사항

### 1. WSL 시스템 의존성 문제는 발생하지 않았다

오케스트레이터가 경고한 "`playwright install-deps` 가 sudo 를 요구해 막힐 수 있다" 시나리오는
**일어나지 않았다.** `playwright install chromium` 만으로 headless Chromium 이 정상 기동했고
(`chromium.launch({headless:true})` → 페이지 렌더 → screencast 동작), `install-deps` 를 실행할
필요가 없었다. Playwright 1.63 의 chromium-headless-shell 이 필요한 라이브러리를 자체 포함한다.
**단 headed 모드(`headless:false`)는 시도하지 않았다** — X 서버가 필요하고 이번 측정 범위 밖이다.

### 2. 좌표 정확도 100% 를 그대로 믿지 않고 대조군을 만들었다 ★

"27/27, 오차 0.00 px"는 **측정이 아무것도 안 해도 나올 수 있는 값**이다. 특히 측정 스크립트가
클라이언트 변환 공식의 역함수로 클릭 지점을 계산하므로, 둘이 같은 방식으로 틀리면 오차가 상쇄된다.
→ 공식을 고의로 깨뜨려(`rect.width` → `canvas.width`) 재측정했고 **9/27 로 떨어지는 것을 확인**했다.
상쇄가 일어나지 않는다는 뜻이다(측정 쪽은 "이미지가 캔버스 박스를 채운다"는 기하학적 정의를 쓰고,
클라이언트 쪽은 실제 DOM 이벤트 좌표를 쓴다). **이 대조군이 없었다면 위 100% 는 근거가 약했다.**

### 3. 입력 드라이버는 정확도로 갈리지 않았다 — 다른 근거로 결정했다

CDP 와 Playwright 가 27/27 로 동률이었다. 02-context 의 "CDP 가 더 직접적" 가설은 정확도 면에서는
확인되지 않았다. IME 가 CDP 를 강제한다는 점과 `down/up` 의 좌표 의미가 더 곧다는 점으로 CDP 를
택했고, **Playwright 경로는 대조군으로 남겼다**(정확도가 같아야 대조군으로 쓸모가 있다).

### 4. 대역폭이 합격 기준에 없었지만 가장 실무적인 발견이었다

세션당 14.6~33.1 Mbps 다. loopback 이라 드러나지 않았을 뿐, 사내망 다중 세션에서는 이게 먼저 막힌다.
합격 기준을 **6배 초과 달성**한 대가이므로, fps 상한으로 회수하면 된다(전달사항 2번).

### 5. `resize` 메시지는 input-bridge 가 처리하지 않는다

`RecorderClientMessage` 의 `resize` 는 브라우저 **상태**를 바꾸는 명령이라 화면 전달 계층이 아니라
세션 수명주기(`session.ts`, Gen-Phase 7)의 책임으로 뒀다. 화면 전달 계층이 브라우저 상태를 바꾸면
1번 방식으로 후퇴할 때 교체 범위가 이 두 파일 밖으로 새어 나간다.

### 6. 범위 준수

- Gen-Phase 4 이후 Task 는 **구현하지 않았다.** `apps/api/src/modules/` · `apps/web/src/pages/` ·
  `injected.ts` · `step-mapper.ts` 는 만들지도 건드리지도 않았다.
- `docker-compose.yml` 의 `TESTFLOW_` 접두사 변수와 `packages/db/src/cli/guard.ts` 는 **무수정**.
- 한글 IME 는 **손대지 않았다**(A안 인터페이스만 존재, 미호출·미측정).
- PoC 전용 파일 5개는 **각 파일 상단 주석에 "PoC 전용 임시물 / 제품 코드 아님 / 승격 위치"를 명시**했다.
