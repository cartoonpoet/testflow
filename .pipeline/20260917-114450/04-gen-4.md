## ConfigModule / 환경변수 로딩 결정 ★

### 확정한 우선순위 (높은 쪽이 이긴다)

```
1. 앰비언트 프로세스 환경변수  (DB_HOST=... node dist/main.js, 컨테이너 env, CI)
2. 레포 루트 .env              (envFilePath 로 절대 경로 고정)
3. apps/api/src/common/config/env.ts 의 zod 기본값 (= .env.example 값)
```

`ConfigModule.forRoot({ override: false })` 로 **명시 고정**했다. 기본값도 `false` 지만
"우연히 그렇게 동작하는 것"과 "그렇게 하기로 정한 것"은 다르므로 옵션을 직접 적었다.

**옵션은 추측하지 않고 `node_modules/@nestjs/config` 소스를 직접 읽어 정했다.** 핵심 두 줄:

```js
// config.module.js
config = options.override ? { ...process.env, ...config } : { ...config, ...process.env };
if (options.validate) { const v = options.validate(config); this.assignVariablesToProcess(v, options.override); }
```

→ ① `override` 가 `.env` ↔ 앰비언트 승부를 가르고, ② `validate(config)` 는 **병합이 끝난 값**을
받으며 ③ `process.env` 반영은 `validate` **직후**에 일어난다. 이 세 가지가 아래 설계의 근거다.

| 옵션 | 값 | 이유 |
|---|---|---|
| `isGlobal` | `true` | 모든 모듈이 `ConfigService` 를 쓴다 |
| `cache` | `true` | `ConfigService#get` 이 매번 `process.env` 를 훑지 않게 |
| `ignoreEnvFile` | `false` | 로컬 개발은 `.env` 로 돈다 |
| `envFilePath` | `[<repo>/.env]` 절대경로 | ★ `process.cwd()` 를 쓰지 않는다. `yarn workspace … dev` 와 `node apps/api/dist/main.js` 의 cwd 가 달라 `.env` 를 놓친다. `import.meta.url` 기준으로 5단계 상위를 잡았고, `dist/common/config/` 와 `src/common/config/` 의 깊이가 같아 빌드 전후 모두 성립한다 |
| `override` | **`false` (명시)** | 아래 "왜 true 가 아닌가" |
| `validate` | `validateEnv` | zod 검증 + **회사 DB 가드** |

### 왜 `override: true` 가 아닌가 (기각 사유)

`override: true` 면 `.env` 가 앰비언트를 이겨 회사 DB 문제가 구조적으로 사라진다. 그런데
`packages/db` 의 마이그레이션 CLI 는 `node --env-file-if-exists` 를 쓰고 있어 **앰비언트가 이기는
반대 규약**이다. 두 진입점의 우선순위가 갈리면 *"마이그레이션은 회사 DB, API 는 로컬 DB"* 라는
최악의 상태가 조용히 만들어진다.
→ **우선순위는 레포 전체에서 하나로 통일하고, 안전장치는 가드 하나로 일원화**한다.
(오케스트레이터가 요구한 "`DB_HOST=company.internal` 로 기동하면 중단" 동작도 이 선택에서만 성립한다.
`override:true` 였다면 `.env` 가 이겨서 **중단되지 않고 조용히 로컬에 붙었을 것**이다.)

### 회사 DB 가드 — 어디에 어떻게 걸었나

- 위치: `apps/api/src/common/config/env.ts` 의 `validateEnv()` → `assertLocalDatabase()` 호출.

  가드 로직은 여전히 파일 하나뿐이고 마이그레이션 CLI 와 API 가 그것을 공유한다.
- **순서 문제를 처리했다.** 가드와 `createDataSourceOptions()` 는 `process.env` 를 *직접* 읽는데,
  `@nestjs/config` 는 `validate` 를 **`process.env` 에 반영하기 전에** 호출한다. 그대로 두면
  `.env` 에만 있는 키(예: `DB_PORT`)를 가드가 못 본다. → `validateEnv()` 안에서 `override:false` 와

## 이슈 / 결정사항

### 1. zod 검증 방식을 `ZodValidationPipe` 로 통일했다

전역 `ValidationPipe`(ERDify 규약)는 **남겨 두되 실질 검증은 하지 않는다.** 핸들러 파라미터 타입이
class-validator 클래스가 아니라 zod 추론 타입이라 Nest 가 `metatype` 을 `Object` 로 보고 건너뛰기
때문이다. 실질 검증은 `@Body(zodBody(Schema))` / `@Query(zodBody(Schema))` 다.
400 응답에는 `details:[{path,message}]` 를 싣되 **값 자체는 싣지 않는다**(비밀번호 반향 방지).

### 2. `PUT /steps` 를 DELETE+INSERT 로 구현하지 않았다 ★

가장 단순한 구현은 "전부 지우고 다시 넣기"인데, `step_results.step_id` 가 `ON DELETE SET NULL` 이라
**순서만 바꿔도 과거 실행 이력의 스텝 연결이 전부 끊어진다.** id 를 보존하는 대신 중간 상태 충돌을
`SEQUENCE_VACATE_OFFSET`(+1,000,000) 으로 피했다. 계획 함수를 `steps.plan.ts` 로 분리해
DB 없이 7건의 단위 테스트로 고정했다.

### 3. 요청에 섞인 "남의 스텝 id" 를 조용히 새 행으로 만들지 않는다

`planStepReplacement()` 가 **400 으로 거부**한다. 관대하게 처리하면 다른 시나리오의 스텝이 복제되고
`step_results` 가 엉뚱한 곳을 가리키게 된다.

### 4. `code` 채번 규칙 — 한글 기능명은 `GEN` 으로 떨어진다

`TC-<FEATURE>-<3자리>` 의 가운데 토막은 `feature` 에서 **ASCII 영숫자만** 남겨 대문자화한다
(최대 8자). `feature:"AUTH"` → `TC-AUTH-001`. **`feature:"로그인"` 은 남는 글자가 없어
`TC-GEN-001`** 이 된다. 음역(transliteration)은 규칙이 자의적이고 되돌릴 수 없어 넣지 않았다.
시안의 `TC-AUTH-001` 표기를 그대로 얻으려면 기능명을 영문 약어로 적어야 한다. **사용자 확인 필요 항목.**

### 5. `publish` 는 스텝 0개를 거부한다 (계획에 없던 판단)

03-phases 완료기준에는 없지만, 스텝이 없는 시나리오를 발행하면 실행 시 0스텝 run 이 만들어지고
대시보드 `successRate` 를 오염시킨다. 400 으로 막았다. **되돌리려면 지금 지시하라.**

### 6. `redis.config.ts` 가 ioredis 타입을 쓰지 않는다

bullmq 6 는 **자체 `RedisOptions` 인터페이스**를 들고 있어 ioredis 6 의 타입을 그대로 넘기면
`ConnectionOptions` union 이 `RedisConnectionClient` 쪽으로 좁혀지며
"`connect`/`duplicate` 가 없다"는 컴파일 에러가 난다(실제로 겪었다). 두 패키지가 공통으로 받는
평범한 객체 타입(`RedisConnectionConfig`)을 직접 정의해 양쪽에 넘긴다.

### 7. `health` 응답 타입은 contracts 에 두지 않았다

`{status,db,redis,runner}` 는 web·runner 가 공유하지 않는 **운영 진단용** 응답이라
`health.service.ts` 에 로컬 인터페이스로 뒀다. 도메인 타입(`TestStep` 등)의 단일 소스 원칙과는
무관한 범주다. 대시보드에서 쓰게 되면 그때 contracts 로 올린다.

### 8. 범위 준수

- Gen-Phase 5 이후 Task 는 **구현하지 않았다.** `modules/{runs,artifacts,recordings,suites,dashboard}`
  디렉토리 자체가 없고 SSE·Runner·웹 화면도 건드리지 않았다.
- `docker-compose.yml` 의 `TESTFLOW_` 변수 · `packages/db/src/cli/guard.ts` **본문** ·
  `apps/runner/src/record/*` · `apps/runner/poc/*` 는 **무수정**.
- `packages/contracts` 는 **추가만** 했다(기존 필드명·구조 무변경).
- 일회성 검증 스크립트(`env-probe.mjs`)는 실행 후 삭제했고 커밋하지 않았다.
- 다른 레포는 **읽지도 수정하지도 않았다.**
- `git commit` 까지만 했고 **push 하지 않았다**.
