### 무엇이 문제였나 (04-gen-5 이슈 5번)

MySQL 컨테이너가 `time_zone=SYSTEM`(= `TZ: Asia/Seoul`, KST)인데 DataSource 는

```
@@global.time_zone  @@session.time_zone  NOW(3)                   UTC_TIMESTAMP(3)
SYSTEM              SYSTEM               2026-09-17 16:03:04.160  2026-09-17 07:03:04.160
호스트 UTC                                2026-09-17 07:03:04      ← NOW() 가 9시간 앞선다
```

### 어떻게 고쳤나

`docker-compose.yml` 의 **mysql 서비스에만 추가**했다. `TESTFLOW_` 접두사 변수는 한 글자도
건드리지 않았고 회사 `DB_*` 이름으로 되돌리지도 않았다.

```yaml
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
      - --default-time-zone=+00:00     # ← 추가
    environment:
      ...
      TZ: UTC                          # ← Asia/Seoul 에서 변경
```

**두 방법 중 어느 쪽이 실제로 효과가 있는가**를 확인해서 정했다.
`TZ` 만 바꾸면 `time_zone=SYSTEM` 이 컨테이너 OS 시각을 따라가므로 이미지·호스트 설정에
따라 흔들린다. **서버 변수로 직접 못 박는 `--default-time-zone=+00:00` 이 결정적**이고,
`TZ: UTC` 는 에러 로그 타임스탬프 일관성을 위해 함께 뒀다.

| DB 자격증명 | 컨테이너에 있어야 함 | **컨테이너에 없다** |

| 자원 제한 대상 | 전체 | **실제로 메모리를 먹는 것(브라우저)** |

메모리·CPU 를 폭주시키는 주체는 언제나 브라우저다. 제한 대상이 정확히 그것이고,
비밀번호·DB 자격증명은 격리 경계 **바깥**에 남는다. **stdin 규약을 따르지 않은 대신
목적(비밀 노출 차단)은 더 잘 만족한다.** 되돌려야 하면 지시하라.

### ★ 실제로 막혔던 지점 (고쳤다 — 추측 아님)

**증상**: `browserType.connect: WebSocket error: read ECONNRESET` 로 2회 연속 실패
(`RUN-0004`·`RUN-0005` 가 그 이력이다).

**원인**: WSL + Docker Desktop 에서 `-p` 로 퍼블리시한 호스트 포트는 **컨테이너 안의
프로세스가 아직 bind 하기 전부터 TCP 연결을 받아 준다**(Docker 의 포트 프록시가 먼저
listen 한다). 그래서 "포트가 열렸으니 준비됐다"는 판정이 거짓이었다.

**수정**: 포트 확인만으로 판정하지 않고 **컨테이너 로그에 `Listening on ws://` 가 찍혔는지**
먼저 확인한 뒤 포트를 본다(`container.ts` 의 `waitForServerReady`). 추가로 `browser.ts` 에
connect 재시도 5회(0.5s→2.5s 지수 간격)를 뒀다. 수정 후 docker 모드 6/6 통과.
컨테이너가 기동 직후 죽은 경우도 `docker inspect .State.Running` 으로 구분해 즉시 중단한다.

### ★ docker 모드에서 알아야 할 제약 (실측)

컨테이너 안의 `127.0.0.1` 은 **컨테이너 자신의 루프백**이다. 호스트에서 돌리는 대상 사이트를
`baseUrl: http://127.0.0.1:8899` 로 주면 `net::ERR_CONNECTION_REFUSED` 가 난다(실측).
`host.docker.internal`(→ `192.168.65.254`)을 써야 한다. `.env.example` 에 주석으로 남겼다.
사내 스테이징처럼 **네트워크상의 실제 호스트**를 대상으로 할 때는 해당 사항이 없다.

### 기본을 `local` 로 둔 이유

- 이미지가 **3.5GB** 다. 개발 머신·CI 가 이걸 전제하면 아무도 못 돌린다.
- 실행당 **+6.5초** 오버헤드.
- `local` 도 격리를 한다 — `launchPersistentContext(<고유 임시 프로필>)` 로 **실행마다 새
  브라우저 프로세스 + 새 프로필**(쿠키·스토리지·캐시가 실행 간에 안 샌다) + 동시성 상한 +
  하드 타임아웃. `local` 이 못 막는 것은 **메모리·CPU 폭주 하나**뿐이다.
- 전환은 `RUNNER_EXECUTION_MODE=docker` **한 줄**이다. 운영 권장값으로 `.env.example` 에 명시했다.

## Locator fallback 동작 확인

**몇 번째 후보에서 성공했는지 기록이 실제로 남는다.**

성공 시나리오의 스텝 #4 는 primary 를 **일부러 깨진 값**으로 두고 fallback 2개를 달았다:
```json
{ "primary":  {"by":"testid","value":"deliberately-broken-primary"},
  "fallbacks":[{"by":"label","value":"존재하지-않는-라벨"},
               {"by":"role","role":"button","name":"로그인"}] }
```
실행 결과 — **primary 와 fallback[0] 을 모두 건너뛰고 fallback[1] 에서 풀렸다**:
```
#4 로그인 버튼 클릭 — PASS (click (fallback[1]/role))
```
비교군으로 정상 스텝은 `(primary/label)` · `(primary/css)` 로 찍힌다. 즉 기록이
"항상 primary" 같은 상수가 아니라 **실제 해결 경로**를 반영한다.

`resolveLocator()` 가 돌려주는 `ResolvedLocator` 에 남는 값:

| 필드 | 이번 실행값 | 용도 |
|---|---|---|
| `resolvedBy` | `"fallback[1]"` | 사람이 읽는 해결 경로 |
| `index` | `2` | 0 = primary |
| `by` | `"role"` | 후보 종류 |
| `usedFallback` | `true` | ★ **"이 스텝은 불안정하다" 신호** |
| `attempts[]` | `[{index:0,by:"testid",matched:0},{index:1,by:"label",matched:0},…]` | 각 후보가 몇 개 매칭됐는지(진단) |
| `elapsedMs` | — | 해결에 걸린 시간 |

단위 테스트(`locator.spec.ts`, 14건)로 규칙도 고정했다 — primary 유일 매칭, primary 0개 →
fallback 하강 + 번호 기록, **2개 이상 매칭이면 그 후보를 버리고 다음으로**(모호한 후보는
재생을 깨뜨린다), `nth` 지정 후보는 "1개만" 규칙 면제, 늦게 나타나는 요소 폴링 대기.

### 타임아웃 예산을 후보 수로 나누지 않는다

후보마다 `timeoutMs` 를 통째로 쓰면 5후보 × 10초 = **50초**가 된다. 대신 전체 예산 하나를
두고 후보 전체를 120ms 주기로 돌아가며 폴링한다(`count()` 는 대기 없이 즉답한다).
요소가 늦게 나타나는 경우도, 첫 후보가 영영 안 맞는 경우도 같은 상한 안에서 끝난다.

### 3. 운영 배포 시 반드시 할 것

```
1. MySQL time_zone 을 UTC 로. SELECT @@global.time_zone 으로 검증하라.
   (컨테이너가 아니면 my.cnf 의 default-time-zone=+00:00)
2. RUNNER_EXECUTION_MODE=docker 로 전환하고
   docker build -f apps/runner/Dockerfile.exec -t testflow/playwright-exec:1.63.0 .
   를 배포 파이프라인에 넣어라(이미지가 없으면 Runner 가 실행 시점에 명시적으로 실패한다).
3. API 와 Runner 는 같은 호스트 + 같은 ARTIFACT_ROOT. 분리하는 순간
   StorageAdapter 의 S3/MinIO 구현이 필요하다(인터페이스는 이미 있다).
4. RUNNER_CONCURRENCY 는 메모리로 결정하라 — 실측 브라우저 1개당 약 240MiB.
```

### 4. 권고 — `mask.ts` 를 `packages/contracts` 로 승격하라

지금 마스킹 구현이 **2곳**이다(`apps/api/src/common/utils/mask.ts` 와
`apps/runner/src/mask.ts`). "마스킹은 단일 함수" 규율에 어긋나지만, 이번 Gen-Phase 의 제약이
`mask.ts` 를 손대지 말 것이라 옮길 수 없었다. 자세한 사유는 아래 이슈 1번.
**승격하면 Runner 쪽 파일은 통째로 사라진다.**

---

## 이슈 / 결정사항

### 1. ★ 마스킹 구현이 2곳이 됐다 (규율 위반 — 의도적, 승인 필요)

전 Gen-Phase 공통 규율은 "Secret 마스킹은 `apps/api/.../mask.ts` **단일 함수**만 쓴다"다.
그런데 그 파일은 `apps/api` 워크스페이스 안에 있고 **`apps/runner` 는 `apps/api` 를 의존하지
않는다**(앱끼리 서로 import 하지 않는다 — 공유물은 `packages/*` 로 간다).
규율을 지키려면 `mask.ts` 를 `packages/contracts` 로 옮겨야 하는데, 이번 지시의 금지 항목이
**`mask.ts` 무수정**이다.

→ Runner 가 실제로 필요로 하는 **문자열 경로 하나만** 같은 규칙으로 구현했다
(`error_message` 는 언제나 문자열이다. 객체 재귀 순회가 필요한 쪽은 API 의 응답·SSE 경로이고
그건 이미 `mask.ts` 가 한다). 3가지 규칙을 한 글자도 다르지 않게 맞췄다 —
치환 문자열 = `SECRET_MASK`(contracts), 3자 미만 제외, 긴 값부터 치환.
**다음 Gen-Phase 에서 승격을 지시하라.**

### 2. `expect()` 를 쓰지 않고 단언을 직접 구현했다

`expect` 는 `@playwright/test` 패키지에만 있고 이 워크스페이스의 의존성은 코어 `playwright`
**하나**다(확정 버전 목록에도 `@playwright/test` 가 없다). 테스트 러너를 통째로 끌어들여
assertion 3개를 쓰는 것은 비용이 맞지 않는다 → `waitFor` + 폴링으로 구현했다.
동작·타임아웃 의미는 같다.

### 3. ★ `assert_text`/`assert_url` 을 **완전 일치가 아니라 포함 일치**로 했다 (확인 필요)

- `assert_text`: 공백 정규화 후 **포함** 검사
- `assert_url`: 완전 일치 → 접두 일치 → 포함 순으로 완화

이유는 쿼리스트링·세션 토큰·공백이 실행마다 달라지는 화면이 흔해서 완전 일치만 요구하면
거의 쓸 수 없기 때문이다. **대가는 거짓 통과**다 — 기대값 `"성공"` 이 `"실패: 성공하지
못했습니다"` 에도 걸린다. 계획서에 정의가 없어 정했다.
필요하면 `options` 에 `exact: boolean` 을 추가하는 쪽이 정석이다(계약 변경이 필요하다).
**되돌리려면 지금 지시하라.**

### 4. 스텝 결과를 **미리 `pending` 으로 전부 INSERT** 한다

시안 실행 현황 화면이 "완료 ✓ / 실행중 스피너 / **대기 번호**" 3-상태를 그리려면 아직
실행하지 않은 스텝도 행으로 보여야 한다. API 의 `toRunSummary()` 가 pending 을
`currentStep` 에서 제외하는 것도 이 전제 위에 있다(04-gen-5). 그래서 실행 시작 시점에
전량 시딩하고, 진행하면서 `running`→`passed`/`failed` 로 올린다.
"행 수 = 스텝 수"(Task 6.4 완료기준)도 이 방식으로 항상 성립한다.

### 5. 취소·타임아웃은 **브라우저를 즉시 끊는다**

스텝 경계에서만 취소를 보면 `wait 60000ms` 나 30초 타임아웃 스텝이 도는 동안 매달린다.
`RunAbortHandle.onAbort` 에 세션 kill 을 걸어 진행 중인 Playwright 호출이 **즉시 던지게**
했다. 실측 515ms. 그리고 **그 예외를 `failed` 로 기록하지 않는다** — 사용자가 직접 멈춘
실행이 "실패 1건"으로 성공률 통계를 깎으면 안 된다(`skipped` + run status `cancelled`).

### 6. 실행 환경 오류를 `error`, 시나리오 실패를 `failed` 로 분리했다

브라우저 기동 실패·컨테이너 연결 실패는 "시나리오가 틀렸다"가 아니라 "실행 환경이 깨졌다"다.
둘을 같은 status 로 뭉치면 원인 추적이 불가능해진다. `RUN-0004`·`RUN-0005` 가 `error` 로
남은 것이 정확히 이 구분 덕분에 읽히는 이력이다.

### 7. 증적은 **항상 켜고, 성공하면 버린다**

video·trace 는 실행이 끝난 뒤에 소급해서 켤 수 없다. 그래서 녹화·트레이싱은 항상 켠 채로
시작하고, 성공이면 임시 디렉토리째 지운다(`KEEP_ARTIFACTS_ON_SUCCESS=false` 기본).
반대로 하면(실패를 감지한 뒤 켜기) **정작 실패한 그 실행의 증적이 없다.**

### 8. 콘솔·네트워크 로그도 마스킹을 거친다

콘솔에 비밀번호를 찍는 페이지가 실제로 있고, URL 쿼리스트링에 토큰이 실리는 경우도 있다.
`reporter.mask()` 를 거쳐 저장한다. 네트워크 로그는 **응답 본문을 수집하지 않는다** —
본문까지 남기면 개인정보가 통째로 디스크에 남는다. 상한도 뒀다(콘솔 5000줄 / 네트워크 3000건).

### 9. `storage_key` 에 하위 디렉토리를 만들 수 없다

contracts 의 `STORAGE_KEY_PATTERN` 이 `runs/<uuid-36>/<파일명>` 만 허용하고 파일명 문자도
`[A-Za-z0-9._-]` 로 제한한다. **Runner 가 그 밖의 키로 쓰면 파일은 만들어지는데 API 가
400 으로 거부한다 — 증적이 조용히 사라진다.** 그래서 쓰는 쪽에서도 같은 검증을 통과시킨다
(`resolveStorageKey`). 한글 시나리오 이름을 파일명에 쓰려면 `sanitizeFileName()` 을 거쳐야 한다.

### 10. 범위 준수

- Gen-Phase 7 이후 Task 는 **구현하지 않았다.** `record/{injected,step-mapper,session,ws-server}.ts`
  는 만들지 않았고 `record/screencast.ts`·`input-bridge.ts` 는 **열지도 않았다.**
- `apps/web/**` 는 건드리지 않았다.
- `packages/contracts` 는 **추가조차 하지 않았다** — 필요한 이름이 전부 이미 있었다.
- `packages/db` 마이그레이션을 추가하지 않았다(스키마 변경 불필요).
- `docker-compose.yml` 은 **mysql 서비스의 타임존 설정만** 손댔다(사용자 승인 항목).
  `TESTFLOW_` 접두사 변수는 무수정.
- 일회성 검증 스크립트는 전부 삭제했다. 다른 레포는 읽지도 수정하지도 않았다.
- `git commit` 까지만 하고 **push 하지 않았다**.
