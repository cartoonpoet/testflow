## 녹화 세션 토큰 설계 ★

**Gen-Phase 7(Task 7.2)이 이 설계를 그대로 구현해야 한다.**
발급 코드는 `apps/api/src/modules/recordings/recording-token.ts`, 규약 상수는
`@testflow/contracts` 의 `RECORDING_TOKEN_KEY_PREFIX` JSDoc 에 있다.

### 방식

| 항목 | 값 |
|---|---|
| 토큰 | `randomBytes(32)` → **base64url 43자**. URL 안전이라 `?token=` 에 그대로 실린다 |
| 저장 | Redis `testflow:rec:token:<sessionId>` = **`sha256(token)` 의 hex 64자**. 평문은 저장하지 않는다 |
| 만료 | `RECORDING_TOKEN_TTL_SEC = 600`(10분). 응답 `expiresAt` 이 이 값으로 계산된다 |
| 폐기 | `stop` / `DELETE` / 같은 시나리오에 새 세션 생성 시 **키 `DEL`** → 즉시 접속 차단 |
| 전달 | `wsUrl = ws://RUNNER_WS_HOST:RUNNER_WS_PORT/rec/<sessionId>?token=<평문토큰>` |

### Runner 가 검증하는 방법 (Task 7.2 구현 지시)

```ts
// /rec/:sessionId?token=… 핸드셰이크에서
const stored = await redis.get(recordingTokenKey(sessionId));   // contracts 헬퍼
if (!verifyRecordingToken(token, stored)) ws.close(WS_CLOSE_UNAUTHORIZED /* 4401 */);
// verifyRecordingToken = sha256(token) 과 stored 를 timingSafeEqual 로 비교.
// 길이가 다르면 던지므로 먼저 걸러 false 를 돌려준다(구현은 recording-token.ts 참조).
```

세션이 DB 에서 `stopped`/`expired` 인데 토큰만 남아 있는 경우를 대비해
`recording_sessions.status` 도 함께 확인하고, 아니면 `WS_CLOSE_SESSION_GONE`(4404)로 닫는다.

### 왜 HMAC(무상태)이 아니라 Redis(유상태)인가

1. **새 공유 비밀을 늘리지 않는다.** Redis 는 API·Runner 가 이미 공유한다.
   `.env` 에 서명키를 추가하면 `SECRET_ENC_KEY` 를 일부러 뺀 결정(★ 최종 결정 (c))과 결이 어긋난다.
2. **즉시 폐기가 된다.** HMAC 은 만료 시각까지 유효해서 세션을 끝낸 뒤에도 살아 있다.
   녹화는 브라우저 1개를 점유하는 대화형 자원이라 "끝났으면 그 순간 못 붙는다"가 중요하다.
3. **해시만 저장**하므로 Redis 덤프가 유출돼도 접속 가능한 토큰이 나오지 않는다.

비회원제라 **사용자 인증과 무관**하다. 이 토큰이 증명하는 것은 "이 세션에 붙어도 되는 클라이언트인가" 하나뿐이다.

### 제어 채널 (API → Runner)

API 는 WS 를 중계하지 않으므로 Runner 에게 명령할 직접 경로가 없다. `stop`/`DELETE` 는
`recordingControlChannel(sessionId)` = `rec:<sessionId>:control` 로 publish 한다.

```json
{"t": "stop" | "dispose", "sessionId": "<uuid>", "at": "<ISO>"}
```

Gen-Phase 7 의 세션 매니저가 이 채널을 구독해 브라우저를 접어야 한다.
(구독자가 없어도 토큰은 이미 폐기됐으므로 재접속은 막힌다 — 유휴 타임아웃이 최종 방어선이다.)

## SSE 이벤트 규약 ★

**Gen-Phase 6 `reporter.ts` 가 이 절차 그대로 publish 해야 한다.** 규약 전문은
`packages/contracts/src/events.ts` 의 `RunEventEnvelopeSchema` JSDoc 에 있다.

### Redis 키

| 용도 | 키 | 헬퍼 |
|---|---|---|
| pub/sub 채널 | `run:<runId>` | `runEventChannel(runId)` |
| 재전송 버퍼 (List) | `run:<runId>:events` | `runEventBufferKey(runId)` |
| 순번 카운터 | `run:<runId>:seq` | `runEventSeqKey(runId)` |
| 취소 신호 채널 | `run:<runId>:cancel` | `runCancelChannel(runId)` |

버퍼 상한 `RUN_EVENT_BUFFER_MAX = 500`, TTL `RUN_EVENT_BUFFER_TTL_SEC = 3600`.

### 봉투(envelope) — 채널과 버퍼에 **같은 바이트**를 넣는다

```json
{"seq": 4, "payload": {"event": "run.finished", "runId": "…", "status": "failed", …}}
```

`seq` 를 `RunEvent` 안에 넣지 않은 이유: `seq` 는 전송 계층의 관심사(재전송 순번)이지
이벤트 내용이 아니다. 봉투로 감싸면 버퍼와 채널에 동일 바이트를 넣을 수 있어
재연결 중복 판정이 `seq` 비교 하나로 끝난다.

### 발행 절차 (순서가 중요하다)

```
seq = INCR  run:<id>:seq
      EXPIRE run:<id>:seq 3600
body = JSON({seq, payload})
      RPUSH  run:<id>:events body
      LTRIM  run:<id>:events -500 -1
      EXPIRE run:<id>:events 3600
      PUBLISH run:<id> body          ← ★ 반드시 버퍼에 넣은 다음
```

publish 를 먼저 하면 구독자가 이벤트를 받은 직후 버퍼를 읽었을 때 그 이벤트가 아직 없어
재연결 재전송에 구멍이 생긴다.

### 이벤트 5종 (contracts `RunEventSchema`, 판별자 `event`)

| `event` | payload 주요 필드 |
|---|---|
| `run.status` | `runId, status, runnerId?, at` |
| `step.started` | `runId, sequence, name, totalSteps, at` |
| `step.finished` | `runId, sequence, result(StepResult 전체), at` |
| `run.finished` | `runId, status, passedSteps, totalSteps, durationMs, errorMessage, at` |
| `artifact.ready` | `runId, type, artifact(Artifact 전체), at` |

### SSE 프레임 형태

```
retry: 3000

: connected

id: 4
event: run.finished
data: {"event":"run.finished","runId":"…","errorMessage":"… input[value='••••••••'] …"}

: ping            ← 15초마다
```

### `Last-Event-ID` 재연결

1. **먼저 채널을 구독**하고 들어오는 이벤트를 메모리에 쌓는다.
2. 그다음 `LRANGE` 로 버퍼를 읽어 `seq > Last-Event-ID` 인 것만 내보낸다.
3. 1번에서 쌓인 것을 `seq` 중복을 걸러 내보낸다.

순서가 반대면(버퍼 먼저 → 구독 나중) 그 사이 발행분이 영구히 사라진다.
`Last-Event-ID` 헤더 외에 `?lastEventId=` 쿼리도 받는다(`curl` 수동 테스트용).
버퍼 500건을 넘겨 밀려난 이벤트는 재전송할 수 없다 — 그때는 클라이언트가
`GET /api/runs/:id` 로 전체 상태를 다시 읽어야 한다.

### 마스킹 3중 방어 (★ 설계 변경 — 검증 중 발견)

| 층 | 무엇을 막나 | 어디서 |
|---|---|---|
| ① 계약 파싱 | 스키마에 **없는 키를 통째로 버린다**. Runner 가 실수로 `password` 필드를 붙여도 클라이언트까지 못 간다 | `RunEventEnvelopeSchema.safeParse` |
| ② **값 기반** | Playwright 에러에 박힌 **비밀번호 평문**. 키 이름이 없으므로 이 경로로만 잡힌다 | `maskSecrets(payload, collectSecretValues(job.data.variables))` |
| ③ 키 기반 | `password\|token\|secret\|…` 이름의 필드 | `maskSecrets` 내부 |

②의 Secret **값**은 **이미 Redis 에 있는 BullMQ job 페이로드에서 읽는다**(SSE 연결 1회당 1번).
새로 저장하는 것이 없고, job 이 만료됐으면 빈 배열로 떨어져 ①③만 남는다.
처음에는 "API 는 값을 모르니 키 기반만" 으로 만들었는데, **실제로 흘려 보니 그게 가장 중요한
케이스(에러 메시지 속 평문)를 전혀 못 막는다**는 것이 드러나 바꿨다.

Runner 의 `reporter.ts` **도** publish 전에 같은 마스킹을 해야 한다(Task 6.4) —
DB(`error_message`)에 남는 값은 SSE 를 거치지 않기 때문이다. 두 겹 다 필요하다.

### ★ 마스킹이 SSE payload 에서 실제로 동작하는가

두 케이스를 실제로 흘려 보냈다.

1. **에러 메시지 속 평문**(Runner 가 마스킹을 빼먹은 상황 가정) — 큐에 `testUser.password=hunter2SuperSecret`
   가 들어 있는 run 에 아래를 publish:
   ```
   errorMessage: "locator.fill: Timeout 10000ms exceeded.\nCall log: waiting for locator(\"input[value='hunter2SuperSecret']\")"
   ```
   → 클라이언트가 받은 값:
   ```
   "errorMessage":"locator.fill: Timeout 10000ms exceeded.\\nCall log: waiting for locator(\"input[value='••••••••']\")"
   ```
   수신 전문에서 `hunter2SuperSecret` **0회**.
2. **스키마에 없는 `password` 키를 붙여 publish** → 수신 payload 에 그 키 자체가 **존재하지 않는다**
   (계약 파싱이 버렸다). 이 발견 때문에 마스킹을 3중으로 정리했다.

## 이슈 / 결정사항

### 1. `CreateRunDtoSchema` 를 고치지 않고 `CreateRunRequestSchema` 를 새로 만들었다 ★

지시는 "`baseUrl` 은 요청값 우선, 없으면 `projects.base_url`" 인데 기존 `CreateRunDtoSchema` 는
`baseUrl` 이 **필수**다(04-gen-2 Task 2.3). 기존 스키마의 구조를 바꾸지 말라는 제약이 있어
**선택 필드 버전을 추가**하고 기존 것은 한 글자도 건드리지 않았다.
의미도 이 편이 정확하다 — `CreateRunRequest` 는 "요청 body", `CreateRunDto` 는 "기본값이 채워진 뒤"다.
큐로 나가는 `RunJobData` 는 언제나 `baseUrl`·`envLabel` 이 채워진 상태다.

### 2. ★ `.gitignore` 의 `artifacts/` 가 소스 디렉토리를 통째로 삼키고 있었다

`apps/api/src/modules/artifacts/` 를 만들었는데 `git status` 에 나타나지 않았다.
`.gitignore` 의 `artifacts/` 는 **어느 깊이든** 매칭되는 패턴이라 모듈 소스 5개 파일이
조용히 무시되고 있었다. `/artifacts/`(선행 슬래시 = 레포 루트 한정)로 고쳤고,
`git check-ignore` 로 ① 증적 디렉토리는 여전히 무시되고 ② 소스는 추적됨을 확인했다.
**이걸 못 잡았으면 Task 5.3 코드가 통째로 커밋에서 빠졌다.**

### 3. 같은 시나리오에 `live` 세션이 있으면 409 가 아니라 **폐기 후 재발급** 한다

409 로 막으면 브라우저 새로고침 한 번, 혹은 Runner 가 죽어 `live` 행이 남은 것만으로
테스터가 그 시나리오를 **영구히 녹화할 수 없게 된다**(API 는 Runner 상태를 알 방법이 없다).
새 세션 생성 시 기존 `live` 를 `expired` 로 바꾸고 토큰을 폐기한 뒤 새로 발급한다.
**되돌리려면 지금 지시하라.**

### 4. 실행 취소는 "큐에 있으면 확정, 실행 중이면 신호만"

큐에서 꺼내지 않은 job 은 API 가 지우고 `cancelled` 로 확정한다(실측: `EXISTS bull:run:<id>` → 0).
이미 `running` 이면 컨테이너를 kill 할 수 있는 건 Runner 뿐이라 취소 채널로 신호만 보내고
**상태 확정은 Runner 에게 맡긴다**. API 가 먼저 `cancelled` 로 바꿔 버리면 Runner 가 나중에
`passed` 로 덮어써 상태가 되돌아가는 사고가 난다.

### 5. ★ 타임존 불일치를 발견해 `runs` 범위 안에서만 고쳤다

`runs.queued_at` 이 `DEFAULT CURRENT_TIMESTAMP(3)` 로 채워지고 있었는데, MySQL 컨테이너는
`time_zone=SYSTEM`(KST)이고 DataSource 는 `timezone: "Z"` 라 **로컬 벽시계 값이 UTC 로 읽혔다.**

```
DB 원시값       2026-09-17 15:42:47.362     (KST 벽시계)
API 응답        2026-09-17T15:42:47.362Z    (9시간 미래)
같은 행 finished_at (Node 가 쓴 값)  2026-09-17T06:52:27Z   ← 9시간 과거. finished_at < queued_at
```

이번 범위에서 두 곳을 고쳤다.
- `runs` INSERT 시 **`queuedAt` 을 앱에서 명시 지정**(DB 기본값에 맡기지 않는다). 수정 후 실측:
  DB `06:52:26.231` = API `06:52:26.231Z` = 호스트 UTC `06:52:27` → 일치.
- 대시보드 기간 경계에서 **`CURDATE()` 를 쓰지 않는다.** Node 가 로컬 자정을 `Date` 로 계산해
  파라미터로 넘긴다(`startOfRange()`, 단위 테스트 4건).

**남은 문제(이번 범위 밖)**: `scenarios`·`suites`·`recording_sessions`·`step_results` 의
`created_at`/`updated_at`/`started_at` 은 여전히 DB 기본값이라 9시간 어긋난 값이 나간다.
실측 예: `GET /api/scenarios` 의 `updatedAt = 2026-09-17T15:15:33.000Z`.
`RUN-0001`~`0006` 도 이 수정 **이전에** 만들어져 `queued_at` 이 어긋나 있고, 그래서
`GET /api/runs` 정렬이 `RUN-0007`(정상 UTC)보다 앞선다.
**권고 해결책 2가지 중 하나를 다음 Gen-Phase 에서 정해야 한다** —
① `docker-compose.yml` 의 mysql 서비스에 `TZ=UTC`(또는 `--default-time-zone=+00:00`) 지정,
② 모든 엔티티에서 DB 기본값을 걷어내고 앱이 항상 시각을 넣는다.
①이 한 줄이지만 **compose 수정은 이번 지시의 금지 항목과 인접**해 손대지 않았다.
**사용자 확인 필요 항목.**

### 6. SSE 를 Nest 의 `@Sse()` 로 만들지 않았다

`id:` 부여 · `Last-Event-ID` 재전송 · `:ping` 주석 keep-alive · `X-Accel-Buffering` 헤더를
전부 직접 제어해야 하는데 Observable 래퍼 뒤에서는 그 넷이 모두 우회 코드가 된다.
`@Res()` 로 응답을 직접 쓴다. 대신 **스트림을 열기 전에 run 존재를 확인**한다 —
헤더를 보낸 뒤에는 상태 코드를 바꿀 수 없어 클라이언트가 404 를 알 방법이 없어진다.

`RunEventsService` 가 `RunsService` 를 주입하지 않고 `RunEntity` 리포지토리를 직접 받는 이유도
같은 맥락이다(`runs.service` → `runs.sse` 방향 의존이 이미 있어 `forwardRef` 가 필요해진다).
존재 확인 한 줄 때문에 순환 의존을 만들 이유가 없다.

### 7. 집계 비용 (일정 압박 시 축소 후보 2번 — 사실 기록)

- `summary` = 쿼리 2개(`runs` 조건부 집계 + `scenarios` COUNT), `readiness` = 쿼리 1개.
- 전부 인덱스를 탄다: `queued_at >= ?` 는 `ix_runs_project_queued` 범위 스캔,
  `readiness` 는 `scenarios.last_run_id` 비정규화 컬럼 조인이라 실행 이력 전체를 훑지 않는다.
- **무거워지는 지점**: `runs` 가 수십만 행이 되면 기간 범위 스캔이 커진다.
  그때는 일자별 집계 테이블(`run_daily_stats`)을 배치로 채우는 쪽으로 옮겨야 한다.
  Redis 캐시(30초 TTL)가 더 싸지만 "방금 돌린 실행이 대시보드에 안 보인다"는 체감 문제가 생겨
  MVP 에서는 넣지 않았다.
- `run_code` 채번(`MAX(CAST(SUBSTRING(run_code,5) AS UNSIGNED))`)은 **인덱스를 못 탄다.**
  현재 규모(7행)에서 전체 요청이 20~47ms 라 문제되지 않지만, `runs` 가 커지면 이 쿼리가
  실행 요청 지연의 주범이 된다. 그때는 Redis `INCR` 카운터나 시퀀스 테이블로 옮긴다.
  (코드 주석에도 같은 내용을 남겼다.)

### 8. `successRate` 의 분모를 "종료된 run" 으로 정했다

계획서에 정의가 없어 정했다. 아직 `running`/`queued` 인 run 을 분모에 넣으면
**실행을 돌릴 때마다 성공률이 떨어져 보인다**. 종료된 run 이 0건이면 0 을 돌려준다.
`automatedScenarios` 는 `status='published'` 시나리오 수로 정의했다(발행 = 자동화됐다).
