## 기능 요약

TestFlow는 비개발자 테스터가 코드 없이 E2E 테스트를 만들고 실행하는 사내 전용 웹 플랫폼이다. 테스터가 TestFlow 화면 안에 스트리밍되는 원격 브라우저를 직접 조작하면 그 행동(이동·클릭·입력·선택)이 시나리오 스텝 초안으로 기록되고, 업무 용어로 스텝을 편집·검증 조건을 추가한 뒤 실행을 요청하면 서버의 Playwright Runner가 Chromium(headless)으로 시나리오를 실행한다. 각 스텝의 시작·성공·실패와 소요 시간은 실시간으로 화면에 표시되고, 실패 시 스크린샷·영상·Trace·콘솔 로그가 실행 이력에 자동으로 연결된다. **이번 MVP는 로그인·회원·권한 개념 없이 단일 공용 워크스페이스로 구현한다.**

**시스템 구조 (문서 원안)**
```
React + Vite  →  NestJS API  →  Redis + BullMQ  →  Runner Manager
(작성·실행·결과)  (인증·권한·업무로직·SSE)  (대기열·동시성)  (격리실행·상태수집·타임아웃)

보조: MySQL 8 (프로젝트·시나리오·실행이력) / Playwright + Docker (Chromium) / S3·MinIO (영상·스크린샷·Trace)
```
원칙: **NestJS가 Playwright를 직접 실행하지 않고, Queue를 통해 별도 Runner에 위임한다.**

**데이터 구조**
```
Scenario (id, project_id, name, status, version, created_by)
   └─ 1:N ─ TestStep (action_type, sequence, target JSON, input JSON, options JSON)
                └─ 1:N ─ StepResult (status, duration_ms, error_message, artifact_key)
```
- MySQL: 프로젝트, 사용자, 시나리오, 스텝, 환경, 실행·스텝 결과와 파일 경로
- Redis: 대기 중 작업, Runner 상태, 일시적 실행 이벤트, 동시 실행 제어 정보
- S3/MinIO: 스크린샷, 영상, Trace, 네트워크·콘솔 로그, 생성된 보고서 파일

**비기능 요구사항**
- Security: 실행별 컨테이너 격리, 프로젝트 권한 검사, Secret 암호화·마스킹, 감사 이력
- Reliability: Runner 자원 제한, 실행 타임아웃, 재시도 정책, 비정상 Runner 감지와 작업 회수
- Performance: 일반 API **p95 500ms 이내**, 실행 요청 후 **1초 이내 Queue 등록**, 상태 이벤트 지연 **2초 이내**
- Retention: DB 이력과 Artifact 보존 기간 분리, 프로젝트별 정책에 따라 자동 만료·아카이빙

## 구현 결정사항

- **아키텍처는 요구사항정의서 원안을 그대로 따른다.** React + Vite + TypeScript 프론트 ↔ NestJS API ↔ Redis + BullMQ ↔ 별도 Runner. MySQL 8 주 DB. NestJS가 Playwright를 직접 실행하지 않고 Queue로 Runner에 위임하는 원칙 유지.
- **UI 라이브러리는 shadcn/ui + Tailwind CSS를 사용한다.** 사용자가 "shadcn / Chakra UI / AntD 중 디자인 괜찮은 걸로 골라서 진행"을 위임했고, ① React+Vite+TS와 궁합, ② CSS 변수 기반이라 위 시안 토큰을 그대로 테마에 주입해 시안 외형을 거의 그대로 재현 가능, ③ Chakra/AntD는 자체 디자인 언어가 강해 시안에서 멀어짐 — 이 세 가지 이유로 확정.
- **시안 토큰은 Tailwind 테마 + CSS 변수로 1:1 이식한다.** 위 "디자인 토큰" 표의 HEX를 그대로 쓰고, 반경·높이·letter-spacing 등 수치도 시안값을 유지한다.
- **로그인·회원가입·인증 화면을 만들지 않는다.** 단일 공용 워크스페이스로 동작한다.
- **녹화는 "원격 브라우저 + 화면 스트리밍" 방식으로 구현한다.** 서버가 Playwright 브라우저를 띄우고, CDP로 화면을 실시간 전송해 TestFlow 웹 UI 안에 렌더링하며, 웹에서의 클릭 좌표·키 입력을 원격 브라우저에 역주입한다. 사내 서버 한 대에 배포해 여러 테스터가 웹으로 접속하는 운영 형태이기 때문에, 서버 쪽에 브라우저 창을 띄우는 방식(별도 창 방식)은 사용할 수 없다.
- 녹화 이벤트 수집 파이프라인은 ① 브라우저 기동 → ② 행동 감지(주입 리스너) → ③ Locator 생성(FR-004: role → label → text → test-id) → ④ 업무 문장 스텝으로 변환·적재 순서로 구성한다.
- **실행은 실제 Playwright로 수행한다.** 저장된 JSON 시나리오를 Runner가 해석해 Chromium headless로 실행하고, 스크린샷·영상·Trace를 실제로 생성한다. 시뮬레이션/목업 실행이 아니다.
- 배포 형태는 **사내 서버 단일 배포**를 전제로 설계한다.
- 테스터 화면에 코드·파일명·CSS Selector를 노출하지 않는 문서 원칙을 그대로 지킨다(선택자는 고급 설정에서만).

## UX 결정사항

- **해피패스**: 시나리오 만들기 진입 → 녹화 시작 → TestFlow 화면 안 브라우저 패널에서 대상 서비스를 직접 조작 → 스텝이 실시간으로 좌측에 쌓임 → 녹화 종료 → 스텝 이름·입력값·기대 결과를 인스펙터에서 편집 → 발행 → 실행 요청 → 실행 현황 화면에서 스텝별 진행을 실시간 확인 → 실패 시 증적 확인
- 녹화 중에는 시안의 `record-badge`(`● 기록 종료`)로 현재 기록 상태를 항상 노출한다.
- 실행 상태는 시안의 3-상태 표현을 따른다: 완료 `✓` / 실행 중 회전 스피너 / 대기 스텝 번호.
- 저장·적용·발행 등 사용자 행동의 결과는 시안의 toast로 알린다(우하단, 2.2초).
- 시안이 제공하지 않는 로딩·빈 상태·에러 화면의 구체적 디자인은 이번 논의에서 정하지 않았다 → 다음 Phase에서 시안 토큰 범위 안에서 설계한다.

## 데이터/API 결정사항

- **비회원 식별: 식별하지 않는다.** 단일 공용 워크스페이스로, 모든 시나리오·실행 이력이 접속자 전원에게 공개된다. 익명 세션 쿠키, localStorage 토큰, URL 워크스페이스 토큰 모두 사용하지 않는다.
- 그 결과 다음이 MVP에서 제거된다: 로그인/세션, 프로젝트 멤버와 역할, 권한 검사, `created_by` 기반 소유권, 감사 이력의 행위자 추적, FR-011의 "권한이 있는 사용자" 조건.
- 서버 상태(시나리오, 스텝, 실행 이력, 결과, 증적 경로)는 전부 MySQL에 저장하고 NestJS API로 제공한다. 클라이언트 전용 상태는 UI 편집 중인 임시 값에 한정한다.
- 실행 중 스텝 상태는 문서 원안대로 **SSE**로 전달한다(상태 이벤트 지연 2초 이내 목표).
- 실행 요청은 BullMQ 큐에 등록하고 Runner가 소비한다(실행 요청 후 1초 이내 Queue 등록 목표).
- 데이터 모델은 문서의 `Scenario 1:N TestStep 1:N StepResult` 구조를 따르되, `created_by`는 비회원제에 맞춰 제거하거나 자유 입력 텍스트(작성자명)로 대체한다.
- API 스펙 문서는 현재 존재하지 않는다 → 다음 Phase에서 새로 정의한다.

## MVP 범위

### 포함
- 대시보드 화면 (지표 4종, 최근 실행 목록, 회귀 테스트 준비도, 확인 필요 항목 notice)
- 테스트 시나리오 목록 화면 (검색, 상태·기능 필터, 6열 테이블)
- 시나리오 만들기 화면 (빌더 + 인스펙터, 스텝 추가·순서 변경·삭제, 임시 저장·발행)
- 실행 현황 화면 (실행 요약, 스텝별 실시간 진행, 브라우저 화면, 실행 정보)
- 원격 브라우저 녹화 (화면 스트리밍 + 입력 역주입 + 행동 → 스텝 변환) — FR-002
- Locator 우선순위 저장 (role → label → text → test-id) — FR-004
- 스텝 편집 (업무용 이름, 입력값, 기대 결과, 순서) — FR-003
- 실행 요청 및 대기·진행·완료 상태 — FR-006
- 스텝별 실시간 결과와 소요 시간 (SSE) — FR-007
- 실패 증적: 스크린샷, 실행 영상, Playwright Trace, 콘솔 로그 연결 — FR-008
- **테스트 스위트 묶음 실행 (FR-010)** — 문서상 SHOULD·Phase 2 항목이지만 사용자가 MVP에 포함하기로 결정
- 실행 로그·화면에서의 Secret 값 마스킹 (시안의 `••••••••` 표기 수준)

## 주요 제약 및 주의사항

- **비회원제와 문서 요구사항의 충돌**: 요구사항정의서는 프로젝트 멤버·역할(FR-001), 권한 기반 공유(FR-011), 페르소나 4종, 사내 SSO, `created_by` 컬럼을 전제한다. 이번 MVP는 이를 모두 제거하므로, 나중에 회원제를 도입할 때 **소유권·권한 컬럼을 사후 추가하는 마이그레이션**이 반드시 필요하다. 스키마 설계 시 이 전환을 염두에 둘 것.
- **단일 공용 워크스페이스는 접근 제어가 없다.** 사내 서버에 배포하더라도 URL을 아는 누구나 모든 시나리오와 실행 증적(스크린샷·영상)을 열람할 수 있다. 실제 운영 서비스를 대상으로 테스트하면 화면에 실데이터가 찍힐 수 있으므로, **최소한 네트워크 레벨(사내망 제한)의 차단이 전제되어야 한다.**
- **원격 브라우저 스트리밍 방식은 MVP 중 가장 난이도가 높은 부분이다.** CDP 화면 전송, 입력 좌표 역주입, **한글 IME 조합 중계**, 스크롤, 네트워크 지연 처리가 모두 구현 대상이다. 일정 리스크가 여기에 집중되므로 가장 먼저 PoC로 검증할 것. (참고: 방식 비교 시각화 문서 `recording-options.html` 동봉)
- **"빠르게 만든다"는 요청과 선택된 구성(NestJS + MySQL + Redis/BullMQ + 별도 Runner + 화면 스트리밍 녹화 + 스위트 실행)은 방향이 상충한다.** 비회원제로 줄인 분량보다 녹화 스트리밍과 인프라 구성의 분량이 크다. 일정이 압박될 경우 가장 먼저 줄일 후보는 ① 테스트 스위트 묶음 실행(SHOULD), ② 대시보드 지표의 실데이터 집계이다.
- **FR-005는 MUST인데 관리 화면이 MVP에서 빠졌다.** 변수·Secret을 어디서 입력받을지(시나리오 내부 인라인 vs 별도 화면)가 정해지지 않았다. 마스킹 표시 자체는 유지하되, 입력 경로는 다음 Phase에서 결정해야 한다.
- **실행 환경 관리 화면이 빠졌으나 실행에는 `baseUrl`과 환경 구분값이 반드시 필요하다.** (시안 스텝에 `{{baseUrl}}/login`이 등장하고, 실행 정보에 "환경: 스테이징"이 표시됨) 이 값을 어디서 받을지는 **미결** — 다음 Phase에서 최소 형태(시드 데이터 / 프로젝트 단일 설정 / 실행 요청 시 직접 입력 중 택1)를 결정해야 한다.
- **Artifact 저장소(S3 vs MinIO vs 로컬 디스크)는 미결이다.** 문서에서도 미결로 남아 있고 이번 논의에서도 정하지 않았다. 사내 단일 서버 배포이므로 로컬 디스크 또는 MinIO가 유력하나 확정 필요.
- **배포 서버의 Docker 사용 가능 여부가 미결이다.** 문서의 "실행별 컨테이너 격리" 요구와 직결된다. Docker를 못 쓰면 Runner 격리 방식을 재설계해야 한다.
- 시안에 없는 화면(테스트 스위트 목록 등)은 시안 토큰과 기존 4화면의 패턴(패널·테이블·툴바)을 재사용해 새로 설계해야 한다.
- 성능 목표(API p95 500ms / Queue 등록 1초 / 상태 이벤트 2초)는 문서에 명시된 값이므로 유지한다.
