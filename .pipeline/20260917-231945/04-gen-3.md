## 4. ★ 마스킹 전수 검사 (대조군 포함)

### 4.1 대조 실험 설계 — 왜 단순 grep 으로는 부족한가

처음 검사에서는 **비밀값도 0, 대조군도 0** 이 나왔다. 그건 "마스킹이 됐다"가 아니라
**검사가 아무것도 검출하지 못한다**는 뜻일 수도 있다(패턴 마스킹 `stripStepValue` 가
`Fill` 계열의 **모든** 값을 벗기므로 비밀이 아닌 값도 같이 사라진다).

그래서 **대조군이 반드시 검출되는 위치**를 만들었다 — `expect` 실패 메시지는
Expected·Received 를 **둘 다** 싣는다:

```ts
await page.locator("#username").fill(process.env["TESTFLOW_VAR_username"] ?? "");   // 대조군
await expect(page.locator("#username")).toHaveValue(process.env["TESTFLOW_VAR_password"] ?? ""); // 비밀값 → 실패
```

`variables`: `password = PLAINTEXT-SECRET-E2E-4417` (**`secretKeys:["password"]`**) ·
`username = CONTROL-PLAIN-VALUE-9001` (대조군, secret 아님)

### 4.2 결과 — `step_results.error_message` 실물

```
Error: expect(locator).toHaveValue(expected) failed
Locator:  locator('#username')
Expected: "••••••••"                      ← ★ 비밀값이 SECRET_MASK 로 치환됐다
Received: "CONTROL-PLAIN-VALUE-9001"      ← ★ 대조군은 그대로 남았다 = 검사가 동작한다
Timeout:  5000ms
Call log:
  - Expect "toHaveValue" locator('#username') with timeout 5000ms
  …
```

### 4.3 전수 판정

```
★ 비밀값 step_results (0이어야)                 → 0
★ 비밀값 runs 전 텍스트 컬럼 (0이어야)           → 0
★ 대조군 step_results (>0이어야 = 검사가 동작)   → 1     ← ★ 검사 유효성 증명
★ 녹화 경로 비밀번호 s3cr3t-pw (0이어야)         → 0
★ artifacts.storage_key 비밀값                  → 0
★ Runner/API 로그 파일 비밀값 (grep -c)          → 0 / 0 / 0
```

검사한 컬럼: `step_results.name_snapshot`·`error_message` ·
`runs.{run_code, scenario_name, env_label, base_url, error_message, runner_id}` ·
`artifacts.storage_key` · `scenario_codes.content` · Runner·API stdout 로그 전문.

### 4.4 두 겹으로 막는다 — 어느 하나만으로는 부족하다

| 겹 | 함수 | 막는 것 | 한계 |
|---|---|---|---|
| ① 패턴 | `stripStepValue()` (contracts, Gen-Phase 1) | `Fill "s3cr3t-pw"` → `Fill "***"` | `Expect` 의 Expected/Received 값은 못 막는다 |
| ② 값 | `maskSecretText(x, collectSecretValues(…))` (`RunReporter`) | 에러 메시지 어디에 있든 `••••••••` | `variables` 를 안 넘기면 빈 배열이 된다 |

**①이 유일한 방어선인 경우가 실제로 있다** — 사용자가 `variables` 없이 코드에 값을 직접 쓰면
②가 빈 배열이 된다(01-clarify 제약 1번). 반대로 **②가 유일한 방어선인 경우도 있다** —
`Expect "toHaveValue"` 의 Expected 값(§4.2). 그래서 둘을 다 통과시킨다.

`nameSnapshot` 마스킹은 **`RunReporter.codeStepStarted()`/`codeStepFinished()` 안에서** 걸린다 —
호출부가 잊을 틈을 남기지 않는다(그 클래스의 기존 설계 철학과 같다).

`Expect "toHaveText"` 의 인용부호는 **변형되지 않았다**(§3.1 의 SSE id=15 참조) — matcher 이름이다.

## 10. 이슈 / 결정사항

### 이슈 1 — ★ 자식의 `close` 가 "쓰기 완료"가 아니다 (실측 발견, 수정함)

**증상 두 가지가 같은 원인이었다.**

```
21:52:49.189  취소 신호 → SIGTERM
21:52:49.284  close 이벤트(95ms 후) → 증적 수집(0건) → run.finished → 작업공간 삭제
그 이후       Playwright 가 out/<테스트>/test-failed-1.png 를 쓴다  ← 디렉토리가 되살아난다
```

- **증적을 놓친다** (취소 run 의 증적 0건).
- **`/tmp` 에 작업공간이 남는다** (`ls /tmp/testflow-code-*` 에 1개 잔존 — 완료기준 3.4② 위반).

**수정 2가지**:
1. `ARTIFACT_SETTLE_MS = 700` — `close` 뒤에 쓰기가 가라앉기를 기다린 다음 증적을 훑는다.
2. `dispose()` 를 **재시도**하게 했다(3회 × 400ms, 마지막은 예외를 삼키지 않는다).

**수정 후 실측**: 취소 run 의 증적 **screenshot 1 + video 1 + trace 1**, `/tmp` 잔존 **0개**.

### 이슈 2 — ★ 작업공간 생성 예외가 `try` 밖이라 run 이 `running` 에 영영 남았다 (실측 발견, 수정함)

`createCodeWorkspace()` 가 `try` **앞**에 있었다. 그런데 이 함수는 던진다 —
`assertSafeSpecFilename()`(traversal 3중 방어의 마지막 겹)이다. 결과:

```
DB 에 filename='../../../../../../tmp/EVIL-ESCAPED.spec.ts' 를 직접 INSERT → 실행
→ 파일은 만들어지지 않았다(방어 성공)
→ 그런데 예외가 executeCodeRun 밖으로 나가 run.finished 가 발행되지 않았다
→ RUN-0085 가 status='running' 으로 영구 고착 (SSE 수신 클라이언트도 영구 대기)
```

**방어가 성공한 대가로 실행이 좌초하면 그건 방어가 아니라 새 장애다.**

**수정**: 작업공간 생성을 `try` 안으로 옮기고 `workspace: CodeWorkspace | null` 로 잡아
`finally` 에서 `workspace?.dispose()` 한다. 이벤트 싱크(HTTP 서버) 닫기도 `finally` 로 옮겼다
(기존에는 `catch` 에만 있어 예외 경로에서 포트가 샜다).
**수정 후**: RUN-0087 이 `status=error` + 한국어 메시지로 **정상 종료**한다(§3.6).

(RUN-0085 는 이력이라 지우지 않고 `error` + 사유 메시지로 확정해 뒀다.)

### 이슈 3 — ★ 취소 시 trace 프레임 46건이 "스크린샷 증적"으로 올라갔다 (실측 발견, 수정함)

### 이슈 4 — ANSI 색상 escape 가 `error_message` 에 그대로 들어왔다 (실측 발견, 수정함)

`FORCE_COLOR=0` · `CI=1` 을 줘도 Playwright 의 `expect` 실패 메시지에는 색상 코드가 실려 온다:

```
Error: [2mexpect([22m[31mlocator[39m[2m).[22mtoHaveText…
```

웹은 터미널이 아니므로 `[2m` 이 **글자로 보인다.** `stripAnsi()` 를 만들어 **마스킹과 같은 위치
(DB 쓰기 전)** 에서 벗긴다. 정규식에 ESC(``)를 반드시 포함시켰다 — 빼면
`items[12]meta` 같은 평범한 텍스트까지 지운다(그 대조군을 테스트로 고정했다).

### 결정 1 — `retries: 0` 을 강제한다 (계획서 목록에 없던 추가)

계획서의 "덮어쓰는 것" 목록에는 `retries` 가 없다. 그런데 재시도가 있으면 같은 테스트가 다시 돌아
**같은 스텝이 새 `sequence` 로 두 번 발행되고** `passed_steps`/`total_steps` 가 두 배가 된다
(화면의 "N / M" 이 무의미해진다). 라이브 화면이 1개라는 이유로 `workers: 1` 을 덮는 것과 **같은 종류의
이유**라고 판단해 덮었다. 사용자 값은 테스트로 고정해 두었으니 되돌리기 쉽다.

### 결정 2 — `use.baseURL` 을 **덮지는 않고 기본값으로만** 채운다

계획서는 "`use.baseURL` 은 사용자 값을 유지한다"다. 그대로 두면 실행 요청의 `baseUrl`
(= 화면의 환경 선택, `runs.base_url`)이 **코드 실행에 아무 영향을 주지 않는다** —
`page.goto("/login")` 이 동작하지 않고 `runs.base_url` 이 장식이 된다.
그래서 `mergePlaywrightConfig()` 에서 `baseURL` 기본값을 **`...userUse` 앞에** 놓았다:
사용자 config 에 `baseURL` 이 있으면 **사용자 값이 이긴다**(덮어쓰기가 아니다).
테스트 3건으로 양방향을 고정했다.

### 결정 3 — 증적의 `stepSequence` 는 항상 `null`

Playwright 의 파일명(`test-failed-1.png`)은 **테스트 단위**이지 우리 스텝 번호 단위가 아니다.
억지로 묶으면 틀린 스텝에 증적이 붙는다. `artifacts.step_result_id` 는 NULL 이고
"이 실행의 증적"으로만 보여 준다. (녹화 경로는 실패 스텝에서 직접 찍으므로 값이 있다 — 차이가 남는다.)

### 결정 4 — 작업공간을 `/tmp` 에 두고 `node_modules` 를 심볼릭 링크했다

`/tmp` 에 두면 사용자 spec 의 `import { test } from "@playwright/test"` 가 **해석되지 않는다**
(`/tmp` 위에 `node_modules` 가 없다). 링크 하나로 해결된다 — pnpm 의
`node_modules/@playwright/test` 는 store 로의 링크이고 Node 는 realpath 로 해석하므로
**CLI 와 같은 모듈 인스턴스**가 잡힌다(갈라지면 `did not expect test() to be called here`).
실측으로 확인했고, `dispose()` 가 링크를 따라가 레포의 `node_modules` 를 지우지 않는 것도
테스트로 고정했다(이게 깨지면 레포가 통째로 망가진다).

대안(작업공간을 레포 안에 두기)은 기각했다 — 사용자 코드가 실행되는 디렉토리를 레포 안에 만들면
실패 시 잔존 파일이 `git status` 를 오염시키고 `.gitignore` 관리가 늘어난다.

### 결정 5 — 생성 config 는 `.mjs` 3줄이고 로직이 없다

```js
// TestFlow 가 실행마다 생성하는 파일이다. 직접 수정하지 마라 — 실행이 끝나면 지워진다.
const { resolveInjectedConfig } = await import("file:///…/dist/execute/pw-config.js");
export default await resolveInjectedConfig();
```

병합 규칙을 생성 문자열 안에 쓰면 **단위 테스트가 닿지 않는다**(PoC 는 그렇게 했다).
로직은 `mergePlaywrightConfig()` 한 곳에만 두고 생성 파일은 진입점만 남겼다.
"3줄을 넘으면 로직이 새어 들어간 것"을 테스트로 고정했다.
동적 `import()` 를 쓴 이유: Playwright 의 config 로더가 정적 `import` 의 bare `file://`
specifier 를 해석하지 못할 수 있어, **실측으로 동작을 확인한 형태**만 썼다.

### 결정 6 — reporter 의 step 짝짓기를 숫자 `stepId` 로 바꿨다 (PoC 개선)

PoC 는 `testId|title` 로 begin↔end 를 짝지었다. **같은 테스트에서 제목이 겹치면
(예: `Fill "***"` 두 번 — §3.1 의 #2·#3 이 실제로 그렇다) 짝이 어긋난다.**
Playwright 는 `onStepBegin`/`onStepEnd` 에 **같은 `TestStep` 객체**를 주므로
`WeakMap<TestStep, number>` 로 번호를 붙였다. 누수도 없다.

### 결정 7 — `@playwright/test` 를 `dependencies` 로 옮겼다

`devDependencies` 에 있으면 프로덕션 설치에서 빠지는데, 런타임에 **CLI 를 spawn 하고
사용자 spec 이 import 한다.** 개발 의존이 아니다. 버전은 그대로 `1.63.0`
(`pnpm install` 이 lockfile 의 importer 항목만 옮겼고 패키지 추가·변경 0건).
