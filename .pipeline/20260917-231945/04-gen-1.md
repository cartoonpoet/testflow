## 3. DB 스키마 변경 최종형

### 3.1 마이그레이션 011 (`011-add-scenario-source.ts`) — 3가지

```sql
-- ① scenarios.source_type  (기존 행은 DEFAULT 로 'steps' 백필)
ALTER TABLE scenarios
  ADD COLUMN source_type ENUM('steps','code') NOT NULL DEFAULT 'steps' AFTER status;

-- ② 코드 본문 1:1 테이블
CREATE TABLE scenario_codes (
  id           CHAR(36)     NOT NULL,
  scenario_id  CHAR(36)     NOT NULL,
  filename     VARCHAR(255) NOT NULL,
  content      MEDIUMTEXT   NOT NULL,
  size_bytes   INT UNSIGNED NOT NULL,
  created_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at   DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  CONSTRAINT pk_scenario_codes PRIMARY KEY (id),
  CONSTRAINT uq_scenario_codes_scenario UNIQUE (scenario_id),
  CONSTRAINT fk_scenario_codes_scenario FOREIGN KEY (scenario_id)
    REFERENCES scenarios(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- ③ runs.source_type  실행 시점 스냅샷
ALTER TABLE runs
  ADD COLUMN source_type ENUM('steps','code') NOT NULL DEFAULT 'steps' AFTER browser;
```

`down()` 은 역순(`runs` 컬럼 → `scenario_codes` 테이블 → `scenarios` 컬럼)으로 **실제로 되돌아간다**(실측).

### 3.2 백필 방식 — `UPDATE` 를 돌리지 않는다

`NOT NULL DEFAULT 'steps'` 로 추가하면 기존 행이 전부 `steps` 가 된다. 뒤에 no-op `UPDATE` 를
붙이지 않은 이유: MySQL 8 의 `ADD COLUMN … NOT NULL DEFAULT` 는 **INSTANT** 알고리즘으로 끝나는데
`UPDATE` 를 붙이면 13,266행짜리 `runs` 를 통째로 다시 쓰게 되어 그 이점을 스스로 버린다.
**백필 여부는 추정하지 않고 `SELECT … GROUP BY` 로 실측했다**(아래 검증 로그).

### 3.3 확장 지점 — 나중에 1:N 이 되려면 (요구사항)

세 곳에 남겼다:

1. **PK 가 `scenario_id` 가 아니라 자체 `id`** 다. 1:1 은 `uq_scenario_codes_scenario`
   **UNIQUE 제약 하나로만** 강제한다 → 다중 파일은 그 제약을 `(scenario_id, filename)` 으로
   바꾸는 마이그레이션 하나면 되고 **PK·FK·관계 방향은 그대로다.**
2. **본문의 정체성을 `filename` 이 갖는다**(`ScenarioCodeSchema` 에 포함) →
   `ScenarioCode[]` 가 그대로 파일 목록이 된다. 스키마를 바꿀 필요가 없다.
3. 관계를 **단방향**(owning side = `scenario_codes`)으로 뒀다. `ScenarioEntity` 에 역방향
   `@OneToOne` 을 걸지 않았으므로 1:N 전환 시 `@OneToMany` 를 새로 추가하면 되고
   **기존 필드를 고치지 않는다.**

근거 주석은 `scenario.ts`(`MAX_SCENARIO_CODE_BYTES` JSDoc) · `scenario-code.entity.ts` ·
`011-add-scenario-source.ts` 세 곳에 같은 내용으로 있다.

## 4. import 검증기 — 규칙과 ★한계

### 4.1 규칙

| # | 검사 | code | severity |
|---|---|---|---|
| 1 | 본문이 비었다 | `empty` | error (즉시 반환) |
| 2 | 256KiB 초과 | `too_large` | error |
| 3 | 허용 목록 밖 패키지 (`playwright` 본체 포함) | `import_not_allowed` | error |
| 4 | 상대 경로 (`./`·`../`) | `relative_import` | error |
| 5 | Node 내장 (`fs`·`node:fs/promises`·`child_process` …) | `node_builtin` | error |
| 6 | `test(` 도 `test.describe(` 도 없다 | `no_test` | **warning** (저장을 막지 않는다) |

스캔 형태 **3종**: `import … from "x"` / `export … from "x"` / `import "x"` / `import("x")` / `require("x")`.
AST 파서를 쓰지 않는다 — TS 파서를 API 에 끌어들이면 `.npmrc` 의 `minimum-release-age=1440`
게이트를 또 통과해야 하고, **정확도를 올려도 보안 경계가 되지는 않는다.**

**오탐 방지**: 스캔 전에 주석을 **공백으로 치환**한다(길이·줄바꿈 보존 → 줄·열이 어긋나지 않는다).
문자열·템플릿 리터럴 상태도 같이 따라간다. 주석 처리해 둔 `// import fs from "fs"` 가
오류로 잡혀 저장이 막히면 이 함수의 목적(UX 안내)과 정반대가 된다.

### 4.2 ★ 한계 — 이 검사는 보안 경계가 아니다

파일 상단 주석 · `validateScenarioCode()` JSDoc · 그리고 **통과하는 테스트 3건**에 박아 뒀다:

```ts
require(["f", "s"].join(""));          // 검출되지 않는다
const m = "node:" + "fs"; await import(m);  // 검출되지 않는다
process.env["HOME"]                    // import 조차 아니다 — 애초에 검사 대상이 아니다
```

> **보안은 실행 격리(쟁점 4 · `RUNNER_CODE_EXECUTION_MODE`)가 담당하고,
> 이 검사는 "왜 안 돌아가는지"를 사용자에게 알려 주는 UX 장치다.**

실행 시점에 뚫고 들어간 import 는 `ERR_MODULE_NOT_FOUND` 로 죽고, 그때는
`run.status = error`(실행 환경 오류)로 확정한다 — `failed`(시나리오 실패)가 **아니다**.
이 문장은 README 에도 남겨야 한다(Gen-Phase 6 전달사항).

## 5. `toActionType` 매핑표 + 회귀 테스트 범위

제목은 **API 이름이 아니라 사람이 읽는 라벨**이다. 아래는 PoC `--mode c/d` 로그에서 **실측한 문자열**이다.

| step 제목 (실측) | `ActionType` | | step 제목 (실측) | `ActionType` |
|---|---|---|---|---|
| `Navigate` | `goto` | | `Wait for timeout` | `wait` |
| `Click` | `click` | | `Expect "toHaveText"` | `assert_text` |
| `Double click` | `click` | | `Expect "toContainText"` | `assert_text` |
| `Fill "hong.gildong"` | `fill` | | `Expect "toHaveValue"` | `assert_text` |
| `Fill "s3cr3t-pw"` | `fill` | | `Expect "toBeVisible"` | `assert_visible` |
| `Type "abc"` | `fill` | | `Expect "toBeAttached"` | `assert_visible` |
| `Set input files` | `fill` | | `Expect "toBeEnabled"` | `assert_visible` |
| `Select option` | `select` | | `Expect "toHaveURL"` | `assert_url` |
| `Check` / `Uncheck` | `check` / `uncheck` | | (미분류) | `wait` |
| `Press` / `Hover` | `press` / `hover` | | | |

**회귀 테스트 범위** (`pw-step-title.spec.ts`, 총 20 케이스 + 가드):

- 실측 제목 **20종**을 `it.each` 표로 1:1 고정 (완료 기준 "12종 이상" 충족)
- **★ 미분류(`wait`) 비율 가드** — `wait` 로 떨어지는 제목 수가 기대치(1건)와 다르거나
  전체의 **15%** 를 넘으면 실패한다. Playwright 버전업으로 라벨이 바뀌면 **이 테스트가 먼저 깨진다.**
  (이 장치가 없으면 전 스텝이 조용히 `wait` 가 되어도 실행은 계속 성공해서 아무도 모른다.)
- 대소문자 무관 · 모르는 제목은 지어내지 않고 `wait`
- **마스킹 구분**: `Fill "s3cr3t-pw"` → `Fill "***"` / **`Expect "toHaveText"` 는 변형되지 않음**
  (matcher 이름이므로). 인용부호 다중 케이스 · 마스킹 후에도 매핑이 유지되는지까지 고정.
- `isUserVisiblePwStep`: `depth 0` + `pw:api`/`expect`/`test.step` 만 통과, `hook`/`fixture` 와
  `depth > 0` 은 전부 거름.

### 이슈 1 — `TextEncoder` 를 쓸 수 없다 (해결됨, 기록용)

`scenarioCodeByteLength()` 를 `new TextEncoder()` 로 짰다가 `TS2304: Cannot find name 'TextEncoder'`
로 막혔다. contracts 는 `types: []` + `lib: ["ES2023"]` 라 **DOM/Node 전역이 하나도 없다.**
`lib` 에 `"DOM"` 을 넣으면 `document` 같은 것도 같이 열려 "브라우저·서버 양쪽에서 도는 순수 계약"
규율이 무너진다 → **코드포인트를 직접 세는 순수 계산**으로 바꿨다. 결과는 동일하고 전역 의존이 0이다.
**앞으로 contracts 에 무언가 넣을 때 같은 벽에 부딪힌다 — 전역을 쓰지 말고 계산으로 풀어라.**

### 이슈 2 — 정규식 스캐너의 오탐 위험 (완화함, 잔존)

주석은 공백 치환으로 걸러냈지만, **문자열 리터럴 안의 `import … from "…"` 같은 문장은
여전히 오탐될 여지가 있다**(현재 패턴으로는 재현되지 않았다). 오탐은 사용자의 저장을 막으므로
검출 누락보다 나쁘다. 실제 사용자 코드에서 오탐이 보고되면 **규칙을 좁히는 쪽으로** 고쳐라

CASCADE 확인을 위해 시드 시나리오 1건을 실제로 삭제했다(253 → 252). 개발 DB 의 더미 데이터다.
