## 1. ★ 캔버스 표시 크기 before / after (실측)

측정 방법: 실제 코드 시나리오를 실행해 **라이브 스트림을 받는 상태**에서 `data-testid="live-canvas"` 의 `getBoundingClientRect()` 를 읽었다. 프레임 해상도는 **1280×800**(캔버스 `width`/`height` 속성으로 확인, 아래 §3).
before 는 `main`(8892909)을 그대로 빌드해 `:4174` 로 따로 띄우고, **같은 시나리오·같은 뷰포트**로 잰 값이다.

### 1.1 핵심 수치 — 뷰포트 1440×900

| | 표시 크기(px) | **1280 대비** | 종횡비 | 배수 |
|---|---|---|---|---|
| **before** (`1fr 360px` 우측 패널) | **360.00 × 225.00** | **28.1 %** | 1.600 | — |
| **after** (전폭 무대, 기본) | **1094.39 × 683.98** | **85.5 %** | 1.600 | **× 3.04** |
| **after** (확대 모드) | **1401.59 × 875.98** | **109.5 %** | 1.600 | **× 3.89** |

> 28.1% 는 프레임 안의 12px 글자가 **3.4px** 로 그려진다는 뜻이다. 물리적으로 읽을 수 없다.
> 85.5% 에서는 10.3px, 확대 모드에서는 13.1px 이다. `r3-live-before-01-inline-1440x900.png` 와
> `r3-live-after-01-inline-1440x900.png` 를 나란히 보면 같은 프레임의 "24px / 16px / 12px / 10px 눈금"이
> before 에서는 뭉개지고 after 에서는 10px 줄까지 읽힌다.

### 1.2 뷰포트별 (after, 실측)

| 뷰포트 | 기본 | 1280 대비 | 확대 모드 | 1280 대비 |
|---|---|---|---|---|
| 1366 × 768 | 933.88 × 583.67 | 73.0 % | 1190.39 × 743.98 | 93.0 % |
| 1440 × 900 | 1094.39 × 683.98 | 85.5 % | 1401.59 × 875.98 | 109.5 % |
| 1600 × 900 | 1094.39 × 683.98 | 85.5 % | 1401.59 × 875.98 | 109.5 % |
| 1920 × 1080 | **1280.00 × 800.00** | **100 %** | 1689.59 × 1055.98 | 132.0 % |
| 2560 × 1440 | **1280.00 × 800.00** | **100 %** | **1920.00 × 1200.00** | **150 %** |

1600×900 이 1440×900 과 같은 이유는 **세로가 상한**이기 때문이다(아래 폭 공식의 3번 항). 1920 이상에서 기본 모드가 1280 에서 멈추는 것은 **원본 해상도 상한**(2번 항) 때문이고, 그 위로 키우면 JPEG 업스케일 흐림만 늘어난다.

## 2. 채택한 레이아웃과 근거

### 2.1 채택안 — 라이브를 2단 그리드 **밖으로** 꺼내 상단 전폭

```
before (시안 그대로)                 after (라운드 3)
┌──────────────┬────────┐           ┌────────────────────────────┐
│              │ 라이브 │           │      라 이 브 (전폭)       │  ← 최대 1280px
│  스텝 리스트 │ 360px  │           ├──────────────┬─────────────┤
│              │ 실행정보│           │  스텝 리스트 │ 실행정보    │  ← 시안 1fr 360px 그대로
│              │ 증적   │           │              │ 증적        │
└──────────────┴────────┘           └──────────────┴─────────────┘
```

폭 공식(`globals.css > @utility tf-live-stage`):

```css
width: min(100%, 1280px, calc(76dvh * 1.6));
```

| 항 | 값 | 무엇을 막는가 |
|---|---|---|
| `100%` | 본문 폭 (max 1500px − padding 60px = **1440px**) | 본문 밖으로 삐져나가는 것 |
| `1280px` | **원본 해상도** | 업스케일 흐림 (키워도 안 읽힌다) |
| `calc(76dvh * 1.6)` | 16:10 이라 폭이 곧 높이 | 노트북(900px)에서 요약바·스텝이 전부 화면 밖으로 밀리는 것 |

### 2.2 버린 선택지 (수치로)

뷰포트 1440×900, 본문 실사용 폭 1148px 기준.

| 안 | 라이브 폭 | 1280 대비 | 왜 버렸나 |
|---|---|---|---|
| **A. 상단 전폭** ✅ | 1094 px | **85.5 %** | 채택 |
| B. 좌우 교체 (`라이브 1fr` + `스텝 360px`) | 1148 − 360 − 18 = **770 px** | **60.2 %** | 12px 글자가 7.2px. 아직 읽히지 않는다. **A 대비 폭 −30%** 를 내주고 얻는 것이 "스텝이 옆에 보인다" 하나뿐인데, 스텝 진행은 이미 상단 다크 요약바(`N / M 단계` + pulse)가 말해 준다 |
| C. 2단 유지 + 폭만 확대 (`1fr 560px`) | **560 px** | **43.8 %** | 12px → 5.3px. **여전히 못 읽는다.** 문제를 절반만 고치고 스텝 리스트 폭(570px)까지 같이 깎는다 |
| D. 항상 전체화면 | 1402 px | 109.5 % | 스텝 리스트·증적·실행 정보를 **볼 수 없게 된다.** 실행 현황 화면의 나머지 절반을 버리는 셈이라 기본값이 될 수 없다 → **확대 모드로 분리**(§3) |

### 2.3 "스텝이 화면 밖으로 밀리지 않나"

밀린다 — 1440×900 에서 무대 아래가 접힌다. 대신 **스크롤 없이 보이는 것**이 이렇다.

- 상단 다크 요약바: `실행 성공 / 13 / 13 단계` + 실행 중 pulse (시안 요소 그대로)
- 무대 좌상단: 종료 시 `실행 성공 · 마지막 화면` 배지
- 확대 모드: 캔버스 하단에 겹치는 **진행 스트립**(`실행중 · 3 / 3 단계 · Wait for timeout`)

전체 페이지는 `r3-live-after-08-fullpage.png` 참조 — 무대 아래에 시안의 `1fr 360px` 이 그대로 붙어 있다.

## 3. 확대 모드 설계

### 3.1 ★ 포털(Radix `Dialog`)을 쓰지 않았다 — 쓰면 화면이 깨진다

제약에 "Radix Dialog 가 이미 있으니 재사용하라"가 있었지만 **쓸 수 없었다.** `Dialog.Portal` 은 내용을 `body` 로 옮기고, 그 순간 React 가 `<LiveCanvas>` 를 언마운트 → 새로 마운트한다. 그러면 두 가지가 동시에 깨진다.

1. **캔버스 백버퍼가 날아간다.** 지금까지 그린 픽셀이 사라져 "마지막 프레임 유지"(라운드 2 §1.2)가 무효가 된다 — 확대할 때마다 화면이 검게 깜빡인다.
2. **1회용 라이브 토큰을 다시 받는다.** `useLiveStream` 의 접속 정보 쿼리는 `gcTime: 0` · `staleTime: Infinity` 이고 토큰은 한 번 쓰고 버린다. 리마운트가 곧 `GET /runs/:id/live` 재호출 = 새 소켓이다.

→ **DOM 을 옮기지 않고 CSS 만 바꾼다.** 같은 React 엘리먼트가 같은 자리에 남고, 루트에 `tf-live-backdrop`(`position: fixed; inset: 0; z-index: 40`)이 붙는다. 실측으로 확인: 확대 → `Esc` 닫기 후 `data-live-frame="true"` 유지(`stillHasFrame: true`), 콘솔 에러 0건.

같은 이유로 **크롬 바는 조건부 렌더가 아니라 `hidden` 클래스로 감춘다** — 형제 인덱스가 밀리면 `LiveCanvas` 가 리마운트될 수 있다.

### 3.2 구성

| 요소 | 처리 |
|---|---|
| 진입 | 캔버스 우상단 `크게 보기` 버튼 (`data-testid="live-expand"`). "영상으로 보기" 와 **같은 flex 행**에 넣어 겹침을 구조적으로 제거 |
| 폭 | `min(100%, 1920px, calc((100dvh - 24px) * 1.6))` — 크롬 바(42px)를 회수하고 진행 스트립을 **겹쳐서**(레이아웃 높이 0) 세로를 전부 캔버스에 준다. 상한 1920px = 150% 는 업스케일 흐림의 실용 한계 |
| 스텝 진행 | 캔버스 하단 겹침 스트립 — `● 실행중 · 3 / 3 단계 · Wait for timeout` (실측 텍스트). 진행바는 **안 넣었다** — 바로 옆 `N / M` 과 같은 값이고, 코드 실행은 M 이 커져서 바가 뒤로 물러나 보인다 |
| 닫기 | 버튼 `축소 (Esc)` + **`Esc` 키** (`useExpand` 훅) — 실측 `escClosed: true` |
| 스크롤 잠금 | **JS 없이** CSS 로. `body:has([data-slot="live-stage"][data-expanded="true"]) { overflow: hidden }` — 실측 `getComputedStyle(body).overflow === "hidden"` |
| 포커스 트랩 | 두지 않았다. 확대 화면은 **읽기 전용**이고 조작 요소가 닫기 버튼 하나뿐이라 트랩이 막을 사고가 없다(비밀번호 폼인 `Modal` 과 다른 판단) |

스크린샷: `r3-live-after-02-expanded-1440x900.png`

## 4. 시안에서 **의도적으로 벗어난** 부분

시안 화면 4 원문(01-clarify §화면 4): *"`grid: 1fr 360px` … 우측: 브라우저 목업(`aspect-ratio:16/10`, 다크 크롬 바 + **가짜 로그인 화면**) + 실행 정보 kv 리스트"*

| 시안 | 이번 처리 | 근거 |
|---|---|---|
| 라이브(=목업)를 **우측 360px** 안에 | **본문 전폭으로 분리** | 시안이 거기 둔 것은 **정적 그림**이라 줄여도 잃을 정보가 없었다. 라운드 2가 그 자리를 **실제 1280×800 스트림**으로 바꾸면서 전제가 무너졌다 — 28.1% 에서는 화면 안의 글자가 읽히지 않는다 |
| `grid: 1fr 360px` | **그대로 유지** | 라이브만 밖으로 뺐다. 스텝 리스트 + 실행 정보·증적 2단은 시안 비율 그대로다 |
| 다크 크롬 바 (점 3개 + URL) | **유지**(기본 모드) / **감춤**(확대 모드) | 지금 어느 주소를 보고 있는지 알려 주는 유일한 표시라 화면이 커질수록 더 필요하다. 확대 중에만 감추는데, 42px 을 돌려주면 폭이 67px 늘기 때문이다(16:10 이라 높이 1px = 폭 1.6px) |
| `aspect-ratio: 16/10` | **유지** — 전 뷰포트 실측 1.600 | §6 |
| 가짜 로그인 화면(`.fake-login`) | 부활시키지 않음 | 라운드 2 판단 유지 |
| 브레이크포인트 1050 / 760 | **유지** | §7 |

**녹화(`sourceType === "steps"`) 실행은 시안 그대로 둔다.** Runner 가 그 경로에 스트림을 배선하지 않아 보여 줄 라이브가 없다. 전폭 빈 상자를 세우면 "고장났다"로 읽히므로, 그 경로는 우측 360px 브라우저 목업에 스크린샷·중립 안내만 담는 기존 배치를 그대로 쓴다.

실측 (RUN-0181, 녹화 시나리오):
```json
{"liveStagePresent": false, "sideStillPresent": true,
 "sideStillBox": {"w": 360, "h": 225, "aspect": 1.6}, "errors": []}
```

## 5. ★ 녹화 클릭 정확도 회귀 — 배율 3종 실측

### 5.1 먼저: 공용 컴포넌트를 건드렸는가 → **아니다**

```
$ git diff --stat -- apps/web/src/features/recorder/
(출력 없음 — 0 files changed)
```

`StreamCanvas.tsx` · `frame.ts`(`toRemotePoint`) · `useInputBridge.ts` · `useFrameRenderer.ts` · `@utility tf-stream-canvas` **전부 무변경**이다. 라이브 뷰는 `features/live/` 라는 **형제 폴더**에 별도 캔버스를 갖고 있고(라운드 2 구조), 이번 변경은 그쪽만 건드렸다. 즉 `(clientX - rect.left) * (remoteW / rect.width)` 공식에 닿는 코드가 없다.

### 5.2 그래도 실제로 녹화해서 클릭을 꽂아 봤다

`record-login.html` 의 `confirm-a/b/c` 버튼 중심 좌표를 **1280×800 원격 뷰포트에서 먼저 실측**한 뒤, 배율별 캔버스 rect 로 클라이언트 좌표를 역산해 클릭하고, **실제로 저장된 스텝의 locator** 를 확인했다.

| 배율 | 캔버스 CSS | rect/attr 비 | 표적 원격좌표 | 클릭한 클라이언트 좌표 | **기록된 primary** | 판정 |
|---|---|---|---|---|---|---|
| 100 % | 1280 × 800 | 1.000 | confirm-a (306, 405) | (590, 732) | `{"by":"testid","value":"confirm-a"}` | ✅ |
| 70 % | 896 × 560 | 0.700 | confirm-b (306, 465) | (498, 653) | `{"by":"testid","value":"confirm-b"}` | ✅ |
| 130 % | 1664 × 1040 | 1.300 | confirm-c (306, 525) | (816, 683) | `{"by":"testid","value":"confirm-c"}` | ✅ |

**3종 전부 의도한 요소에 정확히 꽂혔다. 오차 0 요소.** 콘솔 에러 0건.
(130% 는 캔버스가 1664×1040 이라 1440×900 뷰포트 밖으로 나간다 — 2000×1300 뷰포트로 다시 측정했다. 이는 배율 기능의 원래 동작이고 이번 변경과 무관하다.)

## 6. 종횡비 실측

프레임은 1280×800 = **1.6**. `LiveCanvas` 컨테이너가 `aspect-[16/10]`, 캔버스는 `h-full w-full` + **`object-contain` 을 새로 추가**했다(Runner 뷰포트가 바뀌어 프레임 비가 달라져도 눌리지 않고 레터박스가 되게).

| 상태 | 표시 폭/높이 | 비 |
|---|---|---|
| 기본 1440×900 | 1094.39 / 683.98 | **1.600** |
| 확대 1440×900 | 1401.59 / 875.98 | **1.600** |
| 1366×768 · 1600×900 · 1920×1080 · 2560×1440 | (§1.2) | **전부 1.600** |
| 1050 / 760 / 390 | (§7) | **전부 1.600** |
| 녹화 실행 우측 목업 | 360 / 225 | **1.600** |

### 캔버스에 실제 화면이 그려진다 (픽셀 검사)

```json
{"canvasAttr": {"w": 1280, "h": 800},
 "meanLuma": 229.7, "minLuma": 0, "maxLuma": 255, "nonBlackRatio": 1.0,
 "textBand": {"min": 0, "max": 255, "contrast": 21}}
```

- `canvasAttr 1280×800` — 프레임 해상도가 계약대로다.
- `nonBlackRatio 1.0` · `meanLuma 229.7` — **검은 화면이 아니다.** 실제 페이지가 그려졌다.
- `textBand.contrast 21:1` — 글자가 있는 상단 띠(0~110px)의 최대/최소 휘도 대비. 순흑/순백이 둘 다 존재하므로 **글자 획이 소실되지 않았다**(WCAG AAA 기준 7:1 의 3배).

## 12. 이번에 **검증하지 않은** 것 (정직하게)

1. **실제 사람 눈의 가독성.** 픽셀 대비(21:1)와 표시 배율(85.5%)과 스크린샷까지가 한계다. "12px 글자가 10.3px 로 그려진다"는 계산이고, 사용자가 그것을 편하게 읽는지는 사용해 봐야 안다.
2. **1920 이상 실기기.** 뷰포트 1920×1080 · 2560×1440 은 Playwright 논리 뷰포트로만 쟀다. 고DPI 실기기의 물리 픽셀 배율은 재지 않았다.
3. **확대 모드의 스크린 리더 동작.** `role="dialog"` + `aria-modal` + `aria-label` 을 붙였고 포커스 트랩은 의도적으로 뺐다(§3.2). NVDA/VoiceOver 로 읽혀 보지는 않았다.
4. **영상 전환 버튼과 확대 버튼의 동시 표시.** 두 버튼을 같은 flex 행에 넣어 겹침을 구조적으로 제거했지만, 실패 실행(영상 증적 생김) + 확대 상태 조합을 실측하지는 않았다.
5. **`dvh` 없는 구형 브라우저.** `100dvh` / `76dvh` 는 폴백을 두지 않았다. 사내 배포 대상이 Chromium 계열이라는 전제다.
6. **코드 실행기가 `127.0.0.1:4998` 로 나가지 못하는 현상**(§검증 중 관측). 이번 변경과 무관해 우회(`page.setContent`)했고 원인은 파지 않았다. 별건으로 확인이 필요하다.
