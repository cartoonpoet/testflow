### 실측 응답 (발췌)

```
POST /api/projects/…/scenarios {"name":"코드 시나리오 검증","sourceType":"code"}
→ 201 {"code":"TC-CODE-001", …, "sourceType":"code", "version":1}

POST /api/projects/…/scenarios {"name":"녹화 시나리오 검증"}        ← sourceType 생략(라운드 1 웹)
→ 201 {"code":"TC-REG-001",  …, "sourceType":"steps"}              ← 기본값 유지 = 회귀 없음

PATCH /api/scenarios/<code-id> {"sourceType":"steps"}
→ 400 {"details":[{"path":"","message":"Unrecognized key: \"sourceType\""}]}
PATCH /api/scenarios/<code-id> {"name":"…"}   → 200                ← 정상 PATCH 는 그대로

PUT /api/scenarios/<id>/code   (정상 spec 375바이트, 한글 포함)
→ 200 {"filename":"login.spec.ts","sizeBytes":375,…}
GET /api/scenarios/<id>/code   → CONTENT_IDENTICAL=True, sizeBytes 375 == 디스크 UTF-8 375
```

### ★ import 위반 — 400 의 `details` 줄·열이 실제와 일치한다

```
PUT 본문:
  1: import { test } from "@playwright/test";
  2: import fs from "fs";
  3: import x from "./helper";
  4: import { a } from "lodash";

→ 400
{"line":2,"column":16,"severity":"error","code":"node_builtin",
 "message":"Node 내장 모듈은 사용할 수 없습니다. 'fs'","moduleName":"fs"}
{"line":3,"column":15,"severity":"error","code":"relative_import",
 "message":"상대 경로 import 는 지원하지 않습니다(단일 파일 실행). './helper'","moduleName":"./helper"}
{"line":4,"column":19,"severity":"error","code":"import_not_allowed",
 "message":"허용되지 않은 패키지입니다. 사용 가능한 import 는 @playwright/test 뿐입니다.","moduleName":"lodash"}
```

`column` 은 **모듈 문자열 리터럴의 시작 열**이다(줄 2의 `"fs"` 의 `"` 가 16열 — 세어서 맞다).

**경고만 있는 코드는 막지 않는다** (실측):
`import { expect } from "@playwright/test"; console.log("no test here");`
→ `no_test`(warning) 만 나오므로 **200 저장됨**. `hasBlockingIssues()` 가 error 만 본다.

## 3. ★ 라이브 스트림 토큰 설계 — Gen-Phase 4 Runner 가 이대로 검증한다

### 3.1 일반화 — `apps/api/src/common/utils/stream-token.ts` (신규)

04-gen-5 의 녹화 토큰 구현을 **복사하지 않고 한 벌로 합쳤다.**
`recording-token.ts` 는 이제 **이름만 유지하는 얇은 위임**이고, 동작·접두사·TTL 은 불변이다
(`recording-token.spec.ts` **9건을 한 글자도 고치지 않고** 그대로 통과 — 리팩터링의 안전망).

```ts
export type StreamTokenKeyspace = "recording" | "live";

generateStreamToken(): string                       // randomBytes(32).toString("base64url") 43자
hashStreamToken(token): string                      // sha256 hex 64자
matchesStreamTokenHash(token, storedHash): boolean  // timingSafeEqual (길이 불일치 → false, throw 안 함)
streamTokenKey(keyspace, id): string
streamTokenTtlSec(keyspace): number

issueStreamToken(store, keyspace, id):  Promise<{token, expiresAt}>
verifyStreamToken(store, keyspace, id, token): Promise<boolean>
revokeStreamToken(store, keyspace, id): Promise<void>
```

`store` 는 `ioredis` 의 `Redis` 가 아니라 **`StreamTokenStore`(set/get/del 3개)** 다 —
단위 테스트에서 인메모리 가짜를 끼워 **키 공간 분리를 실제로 검증**하기 위해서다.

### 3.2 ★ 키 공간 분리 (쟁점 3)

| keyspace | Redis 접두사 | TTL | 발급 엔드포인트 | WS 경로 |
|---|---|---|---|---|
| `recording` | `testflow:rec:token:<sessionId>` | **600초** | `POST /api/scenarios/:id/recordings` | `/rec/:sessionId` |
| `live` | `testflow:run:token:<runId>` | **120초** | `GET /api/runs/:id/live` | `/live/:runId` |

**Redis 실측** (녹화·실행 토큰을 동시에 발급해 확인):

```
$ redis-cli KEYS "testflow:*:token:*"
testflow:run:token:481f4e14-…       ← 실행
testflow:rec:token:8294bff3-…       ← 녹화

$ redis-cli GET testflow:run:token:481f4e14-…
d0d6ba648692a129…f852               ← hex 64자. 평문 토큰과 다름. sha256(평문) 과 일치 확인
$ redis-cli TTL  testflow:run:token:481f4e14-…   → 119

★ 녹화 토큰 sha256 = 46830d63…d575
★ 실행 키 값       = d0d6ba64…f852
   MATCH = NO  ← 녹화 토큰으로 실행 스트림 키를 만족시킬 수 없다
```

테스트로도 고정했다 (`stream-token.spec.ts`) — **같은 id 로** 녹화 토큰만 발급한 뒤:

```ts
verifyStreamToken(store, "recording", RUN_ID, token) === true
verifyStreamToken(store, "live",      RUN_ID, token) === false   // ★ 뚫리면 여기서 깨진다
```
반대 방향(실행 토큰 → 녹화)과 "한쪽 폐기가 다른 쪽에 영향 없음"도 같이 고정했다.

### 3.3 Runner(Gen-Phase 4)가 지켜야 할 규약

`/live/:runId?token=<평문>` 접속 시 —

1. `GET testflow:run:token:<runId>` → sha256 hex.
2. `sha256(제시 토큰)` 과 **타이밍 안전 비교**. 불일치·부재 → close **4401**(`WS_CLOSE_UNAUTHORIZED`).
3. 그 runId 의 스트림 세션이 없으면 close **4404**(`WS_CLOSE_SESSION_GONE`).
4. ★ **`testflow:rec:token:` 를 읽지 마라.** `verifyStreamToken(store, "live", runId, token)`
   를 쓰면 키 공간이 자동으로 지켜진다. 접두사를 직접 조립하지 마라.

**토큰 회전**: `GET …/live` 를 다시 부르면 **새 토큰이 발급되고 이전 해시는 덮어써져 즉시 무효**다
(키가 하나라 SET 이 곧 회전이다 — 실측 확인). **TTL 만료 후에는 키가 사라져 검증이 반드시 실패한다**
(`PEXPIRE 1` 로 실제 만료시켜 `EXISTS → 0` 확인).

### 3.4 `wsUrl` 조립

```
ws://RUNNER_WS_HOST:RUNNER_WS_PORT/live/<runId>?token=<평문>
실측: ws://127.0.0.1:4100/live/481f4e14-…?token=5fUdEXzN…   (:4100 포함, :4000 미포함)
```

nginx 뒤에서는 **`RUNNER_WS_LIVE_PUBLIC_URL`**(신규 env, 기본 `""`)을 쓴다.
녹화의 `RUNNER_WS_PUBLIC_URL` 을 **재사용하지 않는다** — 그 값은 `/rec` 경로까지 포함한 베이스라
(`wss://…/rec`) 그대로 쓰면 실행 스트림이 녹화 경로로 간다. `.env.example` 에도 추가했다.

`RunJobDataSchema` 에 **`sourceType` 만 추가**했다. 나머지 필드는 전부 그대로다.

```jsonc
// redis-cli HGET bull:run:<runId> data   — 실측 그대로
{
  "runId": "481f4e14-c6e3-47f0-9a70-7c29d4d9927a",
  "projectId": "00000000-0000-4000-8000-000000000001",
  "scenarioId": "2e0a93d1-a25a-44b6-ab04-699c6f32a77f",
  "suiteId": null,
  "batchId": null,
  "batchSequence": 1,
  "baseUrl": "https://staging.example.com",
  "envLabel": "스테이징",
  "browser": "chromium",
  "sourceType": "code",            // ★ 추가된 유일한 필드 — 실행 엔진 분기 키
  "variables": { "testUser.password": "PLAINTEXT-SECRET-9931" },   // ★ 평문은 여기에만
  "secretKeys": []
```

### 4.1 ★ 코드 본문은 큐에 싣지 않는다 — Runner 가 DB 에서 읽는다

**결정: 페이로드에 `scenarioId` 만 있고, Runner 가
`SELECT filename, content FROM scenario_codes WHERE scenario_id = ?` 로 읽는다.**
(`grep "@playwright/test"` → 큐 페이로드에서 **0건** 실측)

근거 3가지:
1. job 은 완료 후 **1시간 남는다**(`removeOnComplete:{age:3600}`). 최대 256KiB 본문을 run 마다
   Redis 에 복제할 이유가 없다 — 스위트 실행이면 곱해진다.
2. **이 페이로드에서 민감한 것은 `variables` 하나**라는 성질을 유지해야 감사가 쉽다.
   본문을 넣으면 "큐에 무엇이 있는가"의 답이 두 겹이 된다.
3. Runner 는 이미 DataSource 를 갖고 있다(`step_results` 를 직접 쓴다). 새 경로가 아니다.

**대가(정직하게 기록)**: 큐 등록 ~ 실행 사이에 사용자가 본문을 고치면 **바뀐 본문이 실행된다**
— `scenario_name`·`base_url` 과 달리 **본문은 스냅샷이 아니다.** 큐 대기는 보통 수 초다.
스냅샷이 필요해지면 `runs` 에 컬럼을 붙이지 말고 `run_codes` 스냅샷 테이블을 새로 둬라
(`runs` 를 뜨겁게 만들지 않기 위해 — 쟁점 1과 같은 이유).

### 4.2 `runs` 스키마는 바꾸지 않았다

`runs.source_type` 은 **Gen-Phase 1 의 마이그레이션 011 이 이미 만든 컬럼**이다. 새 마이그레이션 없음.

```
$ SELECT run_code, source_type, total_steps, status FROM runs WHERE id IN (…);
RUN-0068  steps  1  queued     ← 녹화 (회귀: 라운드 1과 동일)
RUN-0067  code   0  queued     ← ★ total_steps = 0 으로 시작
```

**스텝 0건을 거부하는 규칙은 실행 경로에 없다**(`runs.plan.ts`·`runs.service.ts` 를 읽어 확인).
0건 거부는 **발행(`publish`)에만** 있고 거기서는 `sourceType` 으로 이미 갈랐다 → 우회할 것이 없었다.

### 4.3 혼합 스위트 — `batch_id` 묶음 유지 (실측)

```
$ SELECT run_code, source_type, total_steps, batch_id FROM runs WHERE batch_id='ef26dd5e-…';
RUN-0069  steps  1  ef26dd5e-…
RUN-0070  code   0  ef26dd5e-…      ← 같은 batch, source_type 과 total_steps 만 갈린다
```

### 4.4 ★ `variables` 평문이 DB 에 남지 않는지 — 전수 확인

```sql
SELECT COUNT(*) FROM runs         WHERE CONCAT_WS('|', run_code, scenario_name, env_label,
                                    base_url, IFNULL(error_message,''), IFNULL(runner_id,''))
                                    LIKE '%PLAINTEXT-SECRET-9931%';           → 0
SELECT COUNT(*) FROM step_results WHERE … LIKE '%PLAINTEXT-SECRET-9931%';     → 0
SELECT COUNT(*) FROM scenario_codes WHERE content LIKE '%…%';                 → 0

-- runs 컬럼 전체 (variables 컬럼 자체가 없다)
id, run_code, project_id, scenario_id, suite_id, batch_id, scenario_name, env_label,

```

## 5. 파일 업로드 방식 결정과 근거

**결정: 업로드 전용 엔드포인트를 만들지 않는다. 웹이 `File.text()` 로 읽어
`PUT /api/scenarios/:id/code` 에 `content` 문자열로 보낸다.**

| 후보 | 기각 사유 |
|---|---|
| multipart (`multer`/`busboy`) | **런타임 의존성이 는다.** `.npmrc` 의 `minimum-release-age=1440` 게이트를 또 통과해야 하고, 라운드 1이 끝까지 지킨 "의존성 추가 없음" 기조를 깬다. 얻는 것은 0 — **코드는 어차피 텍스트다.** |
| base64 본문 | 얻는 것 없이 전송 크기를 **33% 늘린다**. 디코드 실패 처리 분기도 새로 생긴다. |
| **텍스트 본문 (채택)** | 붙여넣기 경로와 업로드 경로가 **같은 엔드포인트 하나**를 탄다 → 검증 규칙이 갈릴 수 없다. |

**실동작 확인** — 디스크의 실제 PoC 산출물을 파일로 읽어 올렸다:

```
$ 업로드 파일: apps/runner/poc/r2/pw/specs/codegen-login.spec.ts (1260 bytes)
PUT  → 200 {"filename":"codegen-login.spec.ts","sizeBytes":1260}
GET  → ROUNDTRIP_IDENTICAL = True        ← 디스크 원본과 바이트 일치
```
(= Gen-Phase 1 이 말한 "PoC codegen spec 은 issue 0건" 을 API 경로에서도 재확인한 셈이다.)

**파일명**은 `PutScenarioCodeDtoSchema` 가 이미 막는다 — 별도 검증 코드를 쓰지 않았다:
```
{"filename":"../../etc/passwd"} → 400
  details: [{"path":"filename","message":"파일명은 [A-Za-z0-9._-] 와 .spec.ts 확장자만 허용합니다."},
            {"path":"filename","message":"파일명에 '..' 를 쓸 수 없습니다."}]
```

## 6. ★ 목록 조회가 코드 본문을 끌고 오지 않는지 — 구조적으로 확인

쟁점 1의 핵심 주장을 **응답 바이트로** 검증했다.

```
1) 코드 시나리오에 200KB 본문 저장 (sizeBytes = 204874)
   GET /api/projects/<id>/scenarios?size=20   → 8362 bytes
   grep 'xxxxxxxxxx' (본문 채움 문자) → 0건
   grep '"content"'                  → 0건
   항목 키: [authorName, code, feature, id, lastResult, name, sourceType, status, stepCount, updatedAt]

2) 그 본문을 DELETE 한 뒤 같은 목록 재호출        → 8362 bytes   ← ★ 완전히 동일

3) GET /api/scenarios/<id> (상세)                 → 337 bytes, 'content' 키 없음
```

**200KB 가 DB 에 있든 없든 목록 응답이 같은 8362바이트**다 = 목록 쿼리가 `scenario_codes` 를
조인하지도 읽지도 않는다. 구조로 막혀 있다:
- 목록 SQL 은 원시 SQL 이고 `scenario_codes` 가 FROM 절에 없다.
- `ScenariosService` 에 **`ScenarioCodeEntity` 리포지토리를 주입하지 않았다** —
  본문이 필요한 단 한 곳(`publish` 의 검증)에서만 원시 SQL 로 `content` 컬럼을 읽는다.

## 9. 다음 Gen-Phase 에 전달할 사항

### Gen-Phase 3 (Runner 실행 엔진)

1. **큐 페이로드에 코드 본문이 없다.** `scenarioId` 로
   `SELECT filename, content, size_bytes FROM scenario_codes WHERE scenario_id = ?` 하라.
   행이 없으면 `run.status = error`(실행 환경 오류)로 확정하라 — `failed` 가 아니다.
2. **`sourceType` 으로 분기하라.** `executor.ts` 에서 `job.sourceType === "code"` 면
   `code-executor`, 아니면 기존 interpreter. **기존 경로 코드를 한 줄도 바꾸지 마라**
   (이번에 API 쪽 녹화 경로가 완전 무회귀임을 실측으로 확인해 뒀다 — Runner 도 같은 규율).
3. **`filename` 을 Runner 에서 다시 검증하라.** `ScenarioCodeFilenameSchema` 를 그대로 쓰면 된다.
   API 가 이미 막았지만 **DB 에 직접 INSERT 된 행**이 있을 수 있다(3중 방어 규율).
4. **`runs.total_steps` 는 0 으로 들어가 있다.** Runner 가 스텝 발견에 따라 UPDATE 해야 한다.
5. **본문은 스냅샷이 아니다**(§4.1 대가). 실행 직전에 읽은 값이 그 run 의 본문이다.

### Gen-Phase 4 (라이브 스트리밍)

6. **토큰 검증은 §3.3 그대로.** `verifyStreamToken(store, "live", runId, token)` 를 쓰고
   **접두사를 직접 조립하지 마라.** `stream-token.ts` 는 `apps/api` 에 있으므로 Runner 는
   같은 로직을 구현해야 한다 — 그때 **contracts 의 `liveStreamTokenKey(runId)` 를 반드시 쓰고**,
   `testflow:rec:token:` 를 절대 읽지 마라.
7. **`GET /api/runs/:id/live` 는 종료된 run 에 404 다.** 웹이 실행 종료 후 재발급을 시도하면
   404 를 받는다 — 그때 "마지막 프레임 유지 + 상태 배지"(쟁점 3)로 가야 한다.
8. **TTL 120초.** 스트림이 120초보다 길게 이어지는 경우 **재접속에는 새 토큰이 필요하다.**

### Gen-Phase 5 (Web)

9. **파일 업로드는 `File.text()` → `PUT …/code`** 다. multipart 를 만들지 마라.
10. **400 응답의 `details` 가 `CodeValidationIssue[]`** 이고 줄·열 번호가 들어 있다.

## 10. 이슈 / 결정사항

### 이슈 1 — ★ express 기본 JSON 상한 100KB 가 계약(256KiB)을 막고 있었다 (실측 발견, 수정함)

**증상**: 262KB 본문을 `PUT` 하니 `413 {"statusCode":413,"message":"request entity too large"}`.
우리 검증기에 **닿지도 못했다.** 즉 —
- 계약상 **정상인 101KB 짜리 코드가 413 으로 거부**된다(사용자는 이유를 알 수 없다).
- 256KiB 초과 본문의 400 + `details`(줄 번호 · 한국어) 경로가 **죽어 있었다.**

**수정**: `main.ts` 에 `app.useBodyParser("json", { limit: MAX_SCENARIO_CODE_BYTES * 4 })`.
**전송 상한은 의미 상한보다 반드시 커야 한다** — JSON 이스케이프로 본문이 부풀기 때문이다.
의미 상한은 여전히 `MAX_SCENARIO_CODE_BYTES` 이고 **거부 주체는 `validateScenarioCode()` 하나다.**
수정 후 재측정: 262218바이트 → `400 … "코드 본문이 너무 큽니다. 262218바이트 / 허용 262144바이트."`,
204874바이트(200KB) → **200**.

**잔존 한계**: 제어문자로만 채운 병적인 입력은 이스케이프가 최대 6배로 부풀어 여전히 413 이 된다.
그런 입력은 의미 상한도 넘으므로 거부가 정답이라고 판단했다(주석에 남겼다).
**이것은 라운드 1부터 있던 문제다** — 코드 본문이 생기기 전에는 100KB 를 넘는 요청이 없었을 뿐이다.

### 결정사항 1 — `PATCH` strict 를 **컨트롤러에** 뒀다 (contracts 를 고치지 않았다)

Task 2.1 완료기준 ③은 `PATCH {sourceType}` → 400 이고 근거로 `forbidNonWhitelisted` 를 든다.
그런데 zod 의 기본 동작은 모르는 키를 **조용히 버리는 것**이라 그대로면 200 이 나온다
(사용자는 바뀐 줄 안다). `PatchScenarioDtoSchema` 자체를 strict 로 만들면 **contracts 의 기존
스키마 동작이 바뀌어** web·runner 의 다른 소비자에게 전파된다 → **호출부(`scenarios.controller.ts`)에서
`.strict()` 를 적용**했다. web 이 `{name}` 만 보낸다는 것을 grep 으로 확인했고 실제 호출로도 200 을 확인했다.

### 결정사항 2 — `ScenariosService` 에 본문 리포지토리를 주입하지 않았다

`publish` 가 본문 검증을 해야 하는데, `ScenarioCodeEntity` 리포지토리를 주입하면
**목록 경로에서 실수로 본문을 끌어올 길이 열린다**(쟁점 1이 구조로 막은 것이다).
`ScenarioCodeService` 를 주입하면 그쪽이 `ScenariosService` 를 주입하고 있어 **순환**이 된다.
→ 본문이 필요한 **단 한 곳**에서 원시 SQL 로 `content` 컬럼만 읽는다(§6).

### 결정사항 3 — `apps/web` 테스트 픽스처 1줄을 고쳤다 (범위 이탈, 의도적)

`RunSchema` 에 **필수 필드** `sourceType` 을 추가하면 `apps/web/src/lib/run-events.spec.ts` 의
`detail()` 픽스처가 객체 리터럴이라 `TS2719` 로 typecheck 가 깨진다(실측).
기준선(typecheck 7/7)을 깨는 것이 더 큰 위반이라고 판단해 `sourceType:"steps"` **1줄**을 넣었다.
Gen-Phase 1 의 결정사항 1과 같은 판단이다. **화면 코드는 한 글자도 건드리지 않았다.**

### 결정사항 4 — `RunListItemSchema`·`RunSummarySchema` 에는 `sourceType` 을 넣지 않았다

계획서는 "`RunSchema`(또는 `RunSummarySchema`)"로 열어 뒀다. `RunSchema` 하나로 충분하다 —
`RunDetail` 이 그것을 extend 하므로 상세 화면이 값을 받는다. 대시보드 "최근 실행" 목록
(`RunListItem`)은 라이브 뷰를 열지 않으므로 넣을 이유가 없고, 넣으면 매퍼가 하나 더 묶인다.
필요해지면 그때 **추가**하면 된다(지금 넣는 것이 "추가"고 나중은 아니라는 관계가 아니다).

### 결정사항 5 — `RUNNER_WS_LIVE_PUBLIC_URL` 을 새로 뒀다

녹화의 `RUNNER_WS_PUBLIC_URL` 은 값에 `/rec` 경로가 포함된 베이스다(`recording-token.spec.ts` 가
`wss://testflow.internal/rec/` 로 그 형태를 고정하고 있다). 재사용하면 실행 스트림이 녹화 경로로 간다.
nginx location 도 어차피 따로 잡아야 하므로 값도 따로 두는 것이 맞다고 판단했다.

### 이슈 2 — `runs` 이력 4행이 개발 DB 에 남았다

검증으로 만든 `RUN-0067`~`RUN-0070` 은 삭제하지 않았다(실행 이력은 append-only 이고,
`sourceType` 스냅샷이 시나리오 삭제 후에도 남는지 확인하는 증거이기도 하다).
`scenarios` 는 252행 · `scenario_codes` 는 **0행**으로 되돌렸다.
