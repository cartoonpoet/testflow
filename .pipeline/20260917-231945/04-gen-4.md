### 1.2 ② CDP 노출 — 왜 그대로는 안 되는가 (실측 3단계)

**(a) 제품 기본값(`--remote-debugging-address=127.0.0.1`) + `-p 127.0.0.1:P:P`**

```
② CDP 부착 = false  lastErr=browserType.connectOverCDP: connect ECONNREFUSED 127.0.0.1:46639
① playwright test = 정상 동작(reporter 44건)      ← 실행은 멀쩡하다
```

**(b) `--remote-debugging-address=0.0.0.0` 으로 바꿔도 실패한다**

```
--- 컨테이너 안: DevTools HTTP 엔드포인트 ---
{"Browser":"HeadlessChrome/153.0.8010.12", …
 "webSocketDebuggerUrl":"ws://127.0.0.1:43689/devtools/browser/0b4a6358-…"}   ← 안에서는 정상
--- 컨테이너 안: chrome 인자 ---
--remote-debugging-address=0.0.0.0        ← 적용됐다
--remote-debugging-port=43689
--- 호스트(WSL) ---
curl:            curl: (56) Recv failure: Connection reset by peer
connectOverCDP:  FAIL Error: browserType.connectOverCDP: socket hang up
docker port:     43689/tcp -> 127.0.0.1:43689                                 ← 매핑은 살아 있다
```

`Host:` 헤더를 `localhost:P` / `172.17.0.2:P` 로 바꿔도 **전부 reset** 이다.
→ Host 헤더 검증이 아니라 **peer 주소 검증**이다. Chromium 은 인증 없는 DevTools 를
**루프백에서 온 연결만** 받는다. `0.0.0.0` 은 bind 만 바꾸고 그 검사는 통과하지 못한다.

**(c) 컨테이너 안에서 `0.0.0.0:R → 127.0.0.1:P` TCP 중계 → 통과**

```
=== 호스트에서 relay 포트로 ===
{"Browser":"HeadlessChrome/153.0.8010.12", …
 "webSocketDebuggerUrl":"ws://127.0.0.1:45302/devtools/browser/352611f6-…"}   ← 중계 포트가 박힌다
```

`webSocketDebuggerUrl` 에 **중계 포트**가 들어간다(Chromium 이 Host 헤더를 echo 한다) —
그래서 `connectOverCDP` 의 WS 승격도 그대로 맞는다. **호스트 포트 == 컨테이너 포트**로
퍼블리시하는 것이 전제다(다르면 이 URL 이 어긋난다). 이 성질을 단위 테스트로 고정했다.

**★ 그 결과 `pw-config.ts` 의 `--remote-debugging-address=127.0.0.1` 을 고치지 않았다.**
0.0.0.0 으로 바꾸는 쪽이 간단해 보이지만 ⓐ 동작하지 않고 ⓑ 같은 docker 네트워크의 다른
컨테이너에게 인증 없는 DevTools 를 열어 주는 짓이다.

| 위치 | 평문 있나 | 비고 |

| DB (`step_results`·`runs`) | 없다 | 마스킹 2겹이 컨테이너 경로에서도 동작(§5.3) |

**(a) WSL `/tmp` 은 컨테이너에서 보이지 않는다 — 조용히 빈 디렉토리가 마운트된다**

```

$ docker.exe run --rm -v /tmp/g4/mnttest:/probe alpine ls -la /probe
total 4
drwxr-xr-x 2 root root 40 …  .      ← ★ 비어 있다. 에러도 안 난다
```

Docker Desktop(Windows 엔진)은 WSL 경로를 윈도 경로로 해석한다. 그 결과가
**`No tests found`** 라서 원인 추적이 아주 어렵다. 그래서 `toDockerMountPath()` 가
`/mnt/<드라이브>/…` 를 **명시적으로 변환**하고, 변환할 수 없는 경로(`/tmp`·`/home`)는
**던진다** — 빈 마운트를 조용히 만들지 않는다. 단위 테스트로 고정했다.
→ 그 환경에서는 `RUNNER_CODE_WORKSPACE_ROOT` 를 `/mnt/<드라이브>/…` 로 지정해야 한다.
**리눅스 네이티브 docker 는 기본값(`os.tmpdir()`)으로 된다.**

**(b) 베이스 이미지에 `@playwright/test` 가 없고, WORKDIR 에 설치하면 마운트가 덮는다**

```

```

첫 시도(`WORKDIR /work` 에 설치 → `/work` 를 작업공간으로 마운트)는 이렇게 깨졌다:

```

- /work/specs/e2e.spec.ts
- /root/.npm/_npx/e41f203b7505f1fb/node_modules/playwright/lib/…   ← npx 가 레지스트리에서 새로 받았다
```

→ `/opt/tf` 에 설치하고 **`/node_modules` 로 심볼릭 링크**한다(루트에 직접 `npm install` 은
npm 이 거부한다 — exit 1). 그러면 spec 이 어느 디렉토리에 있어도 해석된다.
작업공간은 `/ws` 로 마운트해 링크와 겹치지 않게 했다.

**(c) 이벤트 싱크를 `0.0.0.0` 에 열어야 한다 — 노출면이 늘어난다**

`127.0.0.1` 로 두면 컨테이너에서 못 닿아 **진행 이벤트 0건**(화면에 스텝이 하나도 안 뜬다).
docker 모드에서만 `0.0.0.0` 에 열고, **실행 1건 동안만** 살아 있으며 **NDJSON 만** 받는다.
`local` 모드는 그대로 `127.0.0.1` 이다. 이것이 docker 모드의 대가 중 하나다.

### 1.6 실행 오버헤드 — 실측 (라운드 1 +6.5초와 비교)

동일한 최소 spec(`goto` + `toBeVisible`) 1건:

| 모드 | `runs.duration_ms` | 요청→종료 관측 |
|---|---|---|
| `local` | **6,784ms** | 7,064ms |
| `docker` | **3,598ms** | 3,721ms |

**★ docker 가 오히려 3.2초 빠르다.** 추측이 아니라 실측이고, 이유도 구조적이다 —
`local` 은 작업공간을 `/tmp` 에 두고 `node_modules` 를 **`/mnt/c` 위의 pnpm store** 로
심볼릭 링크한다(04-gen-3 결정 4). 모듈 해석이 느린 파일시스템을 타는 것이 컨테이너
기동 비용보다 크다. 컨테이너 안에서는 `@playwright/test` 가 overlayfs 에 있다.

라운드 1의 +6.5초는 **다른 설계**의 수치다 — 브라우저 서버 컨테이너를 띄우고
`Listening on ws://` 로그를 기다린 뒤 `chromium.connect()` 를 했다. 여기서는 그 대기가 없다.

⚠️ **일반화하지 마라**: 이 수치는 `/mnt/c` 가 느린 WSL 환경의 것이다.
리눅스 네이티브에서는 `local` 이 더 빠를 것이다(측정하지 않았다).

### 1.8 이미지·docker 가 없으면 — **실행을 거부한다**

`local` 로 조용히 내려가지 않는다. 사용자가 격리됐다고 믿고 신뢰할 수 없는 코드를 넣으면
격리가 없는 것보다 나쁘다. `status = error` + 한국어 안내다:

```
격리 실행 이미지가 없습니다: testflow/playwright-code-exec:1.63.0. 먼저 빌드하세요 —
`docker build -f apps/runner/Dockerfile.code-exec -t testflow/playwright-code-exec:1.63.0 apps/runner`.
격리 없이 돌리려면 RUNNER_CODE_EXECUTION_MODE=local 을 명시해야 합니다
(붙여넣은 코드가 Runner 호스트에서 그대로 실행됩니다).
```

`RUNNER_CODE_EXECUTION_MODE` 는 **`local` 에 정확히 일치할 때만** 격리를 끈다
(`locall`·`lokal`·빈 값은 전부 `docker` 로 붙는다 — 오타로 격리가 조용히 풀리지 않게).
테스트로 고정했다.

`(244,248,247)` = 대상 페이지의 `#f5f7f6` 다. 스크린샷에도

### 2.3 ★ 종료 후에도 마지막 프레임이 남는다 + close 1000

```
[g4] 상태 메시지 = [{"t":"state","state":"between-tests"},{"t":"state","state":"live"},
                   {"t":"state","state":"between-tests"},{"t":"state","state":"live"},
                   {"t":"state","state":"between-tests"},{"t":"state","state":"live"},
                   {"t":"state","state":"between-tests"},
                   {"t":"state","state":"ended","runStatus":"passed"}]
[g4] close = {"code":1000,"reason":"run finished","wasClean":true}
[g4] 종료 후 캔버스 distinctColors=56 center=[244,248,247]     ← ★ 캔버스가 비지 않았다
```

- `ended` 를 보낸 뒤 **1.5초 linger** 후 **정상 종료(1000)** 한다. 비정상 code 를 주면 웹의
  close 분류가 "오류"로 읽고 캔버스를 지운다.
- linger 를 두는 이유는 클라이언트 쪽 경합이다 — 마지막 프레임의 JPEG 디코드가
  비동기라, 프레임 직후 close 가 오면 `onclose` 가 디코드를 앞지른다.
- `LiveStreamRegistry.close()` 는 **linger 를 건드리지 않는다**(`dispose()` 주석). run 이
  끝나자마자 레지스트리에서 내려가는 것이 정상 경로이므로 이 분기가 사실상 기본 경로다.

### 2.4 ★ 테스트 전환 구간 신호 (PoC 가 명시적으로 넘긴 항목)

3개 `test()` 실행에서 `between-tests` **4회** / `live` **3회** 가 발행됐다 —
**완료기준 4.3① (최소 1회) 충족.** 전환 공백의 실측 길이(리스크 5 재현 실행의 타임라인):

```
+     0ms frames=   0 {"t":"state","state":"between-tests"}   ← 연결 직후(첫 프레임 전)
+  5832ms frames=   0 {"t":"state","state":"live"}             ← 첫 프레임
+ 14943ms frames= 121 {"t":"state","state":"between-tests"}    ← 테스트 1 종료(타임아웃)
+ 17449ms frames= 121 {"t":"state","state":"live"}             ← 2.5초 공백 뒤 재개
+ 26651ms frames= 242 {"t":"state","state":"between-tests"}
+ 26766ms frames= 242 {"t":"state","state":"live"}             ← 0.1초 공백
+ 32896ms frames= 323 {"t":"state","state":"between-tests"}
+ 33755ms frames= 323 {"t":"state","state":"ended","runStatus":"failed"}
+ 35259ms frames= 323 {"code":1000,"reason":"run finished"}
```

**전환 공백은 0.1초 ~ 2.5초**다. 긴 쪽은 worker 재시작(§3)이다.

**★ 판정 기준을 "프레임 공백"으로 하지 않았다** — screencast 는 화면이 변할 때만 프레임을
내므로 **가만히 있는 페이지는 프레임이 0장**이다. `page.waitForTimeout(3000)` 중인 정상
테스트가 "다음 테스트 준비 중"으로 표시된다. 그래서 **부착된 page 수**로 판정한다
(그것이 전환 구간의 정의 그대로다). 이 선택을 단위 테스트로 고정했다.

## 3. ★ 리스크 5 — worker 재시작 시 CDP 재바인딩 (PoC 미검증 항목)

### 3.1 재현했다

테스트 1을 **테스트 타임아웃**(`test.setTimeout(9000)` + 존재하지 않는 요소 대기)으로
죽여 Playwright 가 worker 를 교체하게 만들었다. 실측:

```
23:58:47.864  [live] CDP 부착 성공 — 127.0.0.1:43035 (15fps 상한)
23:58:57.041  [live] CDP 연결이 끊겼다 — 브라우저 교체를 가정하고 재바인딩을 시도한다
23:58:59.484  [live] CDP 재바인딩 성공 #1 — 브라우저가 교체됐다(worker 재시작)
23:59:14.985  [live] CDP 연결이 끊겼다 …                      ← 실행 종료(정상)
23:59:15.834  [live] 스트림 종료 — pagesAttached=3 rebinds=1 rebindFail=0
                     frames 323/1471 (스로틀 드롭 1148) bytes=31584169 err=none
run … 종료 — failed (9/10), 증적 3건
```

- **재바인딩은 된다.** 공백 **2.44초**(브라우저 교체 시간), 그 뒤 프레임이 재개된다(121 → 242 → 323).
- `pagesAttached=3` — 재시작을 가로질러 **테스트 3건 전부**에 붙었다.
- **실행은 영향받지 않았다** — 10스텝 중 9 passed, 증적 3건 정상.
- 브라우저 교체는 **worker 재시작에서만** 일어났다. 같은 worker 안의 테스트 경계에서는
  context/page 만 바뀌고 브라우저는 유지된다(그래서 3개 테스트에 `rebinds=1`).
  G1 의 "`projects` 1개까지" 전제가 그대로 값을 했다(04-gen-3 §1.6).

### 3.2 안 되면 어떻게 처리하는가 — 설계와 실측

재바인딩 한도는 **8초**다(첫 연결 30초보다 짧다). 끊긴 사유가 ①worker 재시작 ②실행 종료
둘 중 무엇인지 우리는 구분할 수 없고, ②에서 30초를 기다리면 run 이 끝난 뒤에도 폴링이
돌아 정리가 늦어진다. 8초는 실측 교체 시간(1~3초)의 두 배 이상이다.
한도를 넘기면 `rebindFailures` 를 올리고 **스트림만 포기한다** — 아래가 그 증거다.

## 4. ★ 스트림이 실패해도 실행은 계속된다 (Task 4.4 완료기준 ①)

CDP 포트를 **미리 점유**해 `connectOverCDP` 를 실패시켰다
(`RUNNER_CODE_CDP_PORT` 로 포트를 고정하고 그 포트에 더미 리스너를 띄웠다).

```
[fail] 포트 39999 점유 중 — CDP 부착이 실패해야 한다
[fail] run RUN-0104 status=passed 7/7 err=none        ← ★ 실행은 완주했다
[fail] ★ 받은 프레임 = 0장                            ← ★ 스트림은 실제로 죽었다
  +     0ms {"t":"state","state":"between-tests"}
  + 29910ms {"t":"error","code":"CDP_ATTACH_FAILED",
             "message":"실행 화면에 연결하지 못했습니다. 실행은 계속되며 결과와 증적은
                        정상적으로 기록됩니다."}
  + 42814ms {"t":"state","state":"ended","runStatus":"passed"}
  + 44318ms {"code":1000,"reason":"run finished"}
```

**프레임 0장 + `status=passed 7/7`** 이 같은 실행에서 동시에 성립한다 =
"스트림이 실패해도 실행은 계속된다"가 **음성 대조군을 갖춘 형태로** 확인됐다.
실패는 `{t:"error"}` 로 **뷰어에만** 알리고 `run.finished` 는 정상 발행된다.

이 원칙을 코드로 보장하는 지점 세 곳(`code-executor.ts` 주석에도 있다):
1. 포트 할당 실패 → `cdpPort = null` 로 그냥 진행한다(Gen-Phase 3 와 동일 동작).
2. `startCodeBrowser()` 는 **동기 반환**이고 `await` 하지 않는다 — 30초 폴링을 기다리지 않는다.
3. supervisor 의 예외는 그 안에서 삼켜 뷰어에게만 알린다.

### 5.1 ★ 토큰 키 공간 분리 (쟁점 3) — 종단 실측 10건

| ③ | **★ 라이브 토큰으로 `/rec/`** | **close 4401** `invalid recording token` |

②③ 이 키 공간 분리의 직접 증거다. 경계 전부가 "어느 Redis 키에서 해시를 읽었는가"
하나이고(`testflow:rec:token:` ↔ `testflow:run:token:`), 그 성질을 **실제 키 문자열로**
단위 테스트에도 고정했다(키가 같아지는 리팩터링이 들어오면 거기서 깨진다).

### 5.2 ★ 단방향 — 원격 조작이 테스트를 깨뜨리지 않는다

녹화 프로토콜의 입력 메시지(`mouse`/`key`/`ime`/`resize`) + 깨진 JSON + 바이너리를
`/live/` 로 밀어 넣고, **그것이 닿으면 깨지는 단정문**을 둔 spec 을 돌렸다:

```
[oneway] {"stillOpen":true,"readyState":1,"frames":34,
          "texts":["{\"t\":\"state\",\"state\":\"between-tests\"}","{\"t\":\"state\",\"state\":\"live\"}"],
          "closed":null}
[oneway] run RUN-0101 status=failed 4/5     ← 실패는 5번째 스텝(내 spec 의 잘못된 기대값)
```

- 소켓은 **열려 있고** 프레임도 계속 온다(들어온 메시지를 **파싱조차 하지 않는다**).
- `expect(#username).toHaveValue("KEEP-ME")` 가 **passed**(4/5 중 1~4번) =
  주입한 클릭·키가 **페이지에 닿지 않았다.**
- 서버가 `{t:"error"}` 를 돌려주지도 않는다 — 녹화 경로(`BAD_MESSAGE` 응답)와 다르다.
  코드 실행 스트림에는 클라이언트 메시지 계약이 **없기** 때문이다.

### 5.3 마스킹 — 컨테이너 경로에서도 유지된다

docker 실패 실행(RUN-0109, `variables.password = PLAINTEXT-SECRET-G4-DOCKER-9913`):

```
★ runs.error_message 에 평문? = false
★ step_results 에 평문? = 0건
```

`variables` 를 stdin 으로 넘겨도 `collectSecretValues()` 는 **큐 페이로드**에서 값을 뽑으므로
값 기반 마스킹(겹 ②)이 그대로 동작한다. 패턴 마스킹(겹 ①, `stripStepValue`)도 무관하게 동작한다.

### 5.4 동시 실행 2건 — CDP 포트 충돌 없음 (완료기준 4.1③)

```
[conc] A RUN-0119 passed 4/4 · frames=160 close=1000
[conc] B RUN-0118 passed 4/4 · frames=158 close=1000
[conc] A states=[between-tests, live, between-tests, ended(passed)]
[conc] B states=[between-tests, live, between-tests, ended(passed)]
Runner 로그: [live] CDP 부착 성공 — 127.0.0.1:43039
             [live] CDP 부착 성공 — 127.0.0.1:35291     ← ★ 서로 다른 포트
```

**PoC 는 host 포트에서 파생시켜 충돌했다** — 제품은 실행마다 `findFreeCdpPort()` 로 받는다.
충돌하면 두 번째 실행의 스트림이 **첫 번째 실행 화면**을 보여 준다(조용히 틀린 화면).
`findFreeCdpPort()` 의 "연속 호출이 서로 다른 포트를 준다"를 단위 테스트로도 고정했다.

### 5.5 녹화 경로 회귀 (`/rec/`) — 정상

```
[rec] 세션 생성 201 sessionId=f5fe1de7-… viewport={"w":1280,"h":800}
[rec] opened=true frames=155 bytes=3166493 close=null      ← 8초 구간, 프레임 정상
[rec] stop 200 수집 스텝 1건                               ← 입력 역주입·수집 경로 정상
```

- 프레임 봉투(25바이트)·드롭 상한(256KiB)·핸드셰이크 후 close 규약을 **같은 코드로 공유**한다
  (복사하지 않았다). 봉투 레이아웃을 단위 테스트로 고정했다.
- 녹화 토큰 검증 함수는 **이름을 유지한 채 일반화**했다 —
  `hashRecordingToken`/`verifyRecordingToken` 은 이제 일반 함수의 별칭이고
  **해시·비교 동작은 한 글자도 바뀌지 않았다**(테스트로 고정).
- 기존 `steps` 실행의 격리 기본값(`RUNNER_EXECUTION_MODE=local`)은 **바뀌지 않았다**
  (`codeExecutionMode` 와 서로 간섭하지 않음을 테스트로 고정).

## 9. 이슈 / 결정사항

### 이슈 1 — ★ 토큰을 받자마자 붙으면 **4404** 였다 (실측 발견, 수정함)

```
[oneway] {"stillOpen":false,"frames":0,"closed":{"code":4404,"reason":"live stream session is gone"}}
```

`GET /api/runs/:id/live` 는 **종료되지 않은** run 에 토큰을 준다 — `queued` 도 포함된다.
그런데 스트림 세션은 Runner 가 그 job 을 집어 `runStarted()` 한 뒤에 열린다.
**토큰을 받고 즉시 붙으면 세션이 아직 없다.** 화면은 이 4404 를 "끝난 실행"과 구분할 수 없어
**라이브를 영영 못 보게 된다.**

**수정**: 세션이 없으면 **run 이 살아 있는 동안만** 기다린다(`LIVE_SESSION_WAIT_MS = 15초`,
100ms 폴링 + 1초마다 `runs.status` 재확인). run 이 종료 상태거나 행이 없으면 **즉시 4404** 다
(끝난 실행에 스트림을 열어 주지 않는다는 규약 그대로). 15초는 `concurrency` 상한 때문에
큐에서 잠깐 기다리는 경우를 덮고, 그보다 긴 대기는 화면이 다시 요청하는 것이 맞다
(토큰 TTL 이 120초다).

**수정 후**: `{"stillOpen":true,"frames":34, …}` — 정상 접속(§5.2).

**→ Gen-Phase 5 가 알아야 한다**: 그래도 `onopen` 직후 최대 15초간 프레임이 없을 수 있다.
그 구간은 `{t:"state", state:"between-tests"}` 로 온다.

### 이슈 2 — 취소 실행의 작업공간이 **1건** 남았다 (관측, 재현 안 됨)

중간 빌드로 돌린 취소 실행 1건에서 `/tmp/testflow-code-52f37648-kxSkEd/out/` 만 남았다
(04-gen-3 이슈 1 과 같은 형태 — `close` 뒤 늦은 쓰기).
**최종 빌드로 취소를 3회 연속 돌려 재현을 시도했다**:

```
[leak] #1 RUN-0120 cancelled · /tmp 잔존 0개 []
[leak] #2 RUN-0121 cancelled · /tmp 잔존 0개 []
[leak] #3 RUN-0122 cancelled · /tmp 잔존 0개 []
```

docker 모드도 0개(§1.7). **재현되지 않았지만 "0건"이라고 쓰지 않는다** —
`ARTIFACT_SETTLE_MS`(700ms) + `dispose()` 3회 재시도가 **확률적 방어**라는 뜻이다.
Gen-Phase 6 통합검증에서 다시 볼 항목으로 남긴다.

### 이슈 3 — `docker ps` / `docker inspect` 가 WSL interop 에서 간헐적으로 실패한다

검증 하네스에서 Node `spawn("docker.exe", ["ps", …])` 가 **exit 1 + stderr 비어 있음**으로
죽는 경우를 여러 번 봤다(같은 명령이 bash 에서는 정상). `WSL … ERROR: UtilAcceptVsock:271`
도 한 번 나왔다.

**제품 경로에 있는 영향**: `spawnCodeContainer()` 가 매 실행마다 `docker version` 과
`docker image inspect` 를 부른다. 그것이 이렇게 실패하면 **재시도 없이** `status = error` 가 된다.
docker 모드 실행 28건에서는 발생하지 않았지만 **구조적으로 가능하다.**
→ **Gen-Phase 6 에 재시도(2회) 도입을 남긴다.** 지금 넣지 않은 이유: 실패를 한 번도
관측하지 못한 경로에 재시도를 넣으면 진짜 고장(이미지 없음)의 진단이 2배 느려진다.

### 결정 1 — `between-tests` 를 **page 수**로 판정한다 (프레임 공백이 아니다)

계획서 Task 4.3 은 `"마지막 프레임 이후 N ms 동안 프레임 없음 + page 없음"` 을 제시했다.
그 중 **"프레임 없음" 조건을 버렸다.** 근거: screencast 는 화면이 변할 때만 프레임을 내므로
**정지한 페이지는 프레임이 0장**이다. `page.waitForTimeout(3000)` 중인 정상 테스트가
"다음 테스트 준비 중"으로 표시되면 그건 신호가 아니라 오보다.
**부착된 page 수**가 전환 구간의 정의 그대로다. 임계값이 없어져 튜닝할 값도 사라졌다.
`page` 가 붙었지만 첫 프레임이 아직 안 온 구간도 `between-tests` 로 둔다 — 사용자가 보는 것이
"아직 화면이 없다"라는 점에서 같기 때문이다.

### 결정 2 — 컨테이너 안에 **TCP 중계**를 둔다 (config 를 고치지 않는다)

§1.2 의 실측 3단계가 근거다. 대안(`--remote-debugging-address=0.0.0.0`)은 ⓐ 동작하지 않고
ⓑ 동작한다 해도 같은 docker 네트워크에 인증 없는 DevTools 를 여는 짓이다.
중계는 부트스트랩 프로세스 안의 20줄이고, 실패해도 **테스트를 막지 않는다**(던지지 않는다).

### 결정 3 — `variables` 를 **stdin** 으로 넘긴다 (계획서가 요구한 "노출되지 않는 방법")

계획서: *"`docker inspect` 에 노출되지 않는 전달 방법(예: stdin, tmpfs 파일)을 찾았으면
그것을 쓰고 실측으로 확인하라"*. **stdin 을 택했다.**
- `tmpfs 파일`은 기각: 파일을 만드는 쪽이 호스트라 **평면 디스크에 평문이 한 번 쓰인다**
  (작업공간은 bind mount 다). tmpfs 를 컨테이너 안에 만들어도 거기에 쓸 통로가 또 필요하다.
- stdin 은 **호스트 프로세스 메모리 → 파이프 → 컨테이너 프로세스 메모리** 뿐이다.
- 대가: 부트스트랩이 stdin `end` 를 기다린다 → **호스트가 반드시 닫아야 한다**
  (변수가 없어도 빈 JSON 을 쓰고 닫는다). 안 닫으면 실행이 영영 멈춘다.

### 결정 4 — `RUNNER_CODE_EXECUTION_MODE` 는 `local` 에 **정확히 일치**할 때만 격리를 끈다

`Docker`·`DOCKER`·`locall`·`lokal`·빈 값은 전부 `docker` 로 붙는다.
오타 하나로 격리가 조용히 풀리는 것이 이 설정의 최악 실패 모드다. 테스트로 고정했다.
같은 이유로 **이미지가 없으면 `local` 로 내려가지 않고 실행을 거부**한다(§1.8).

### 결정 5 — `RUNNER_CODE_CDP_PORT` 를 추가했다 (계획서 목록에 없던 것)

CDP 포트를 고정하는 설정이다. 두 용도가 있다 —
① 방화벽이 특정 포트만 허용하는 환경(동시 실행 1건으로 묶어야 한다),
② **고장 주입** — 그 포트를 미리 점유하면 `connectOverCDP` 가 실패한다.
§4 의 "스트림이 실패해도 실행은 계속된다"를 **실제로 실패시켜** 확인하는 유일한 방법이었다.
기본값 `0`(실행마다 빈 포트)을 유지하는 것이 옳고, 그 사실을 `.env.example` 에 적었다.

### 결정 6 — `record/session.ts` 의 `maxFrameRate()` 를 **import** 한다

15fps 상한을 새로 읽지 않는다. 녹화와 실행이 같은 상한을 타야 대역폭 실측(2.28→2.33 Mbps)이
양쪽에서 같은 의미를 갖는다. `session.ts` 는 **수정하지 않았다**(import 만).

### 결정 7 — 뷰어는 **최신이 이긴다** (sink 1개)

계획서 권고대로 sink 1개다. 새 뷰어가 오면 이전 소켓을 정상 종료(1000)하고 교체한다.
거부하는 쪽을 택하지 않은 이유: 새로고침하면 이전 소켓이 아직 닫히지 않은 사이에
사용자가 화면을 못 본다. 관전 기능이 생기면 그때 다중 sink 로 넓힌다.

**③ ★ 보내는 것 — 없다. 단방향이다.**
`useInputBridge`/`useImeBridge` 를 붙이지 마라. 보내도 **무시**되고(파싱조차 하지 않는다)
서버가 오류도 돌려주지 않는다. 그 대신 코드 실행 화면에는 입력 경로가 **없다**는 것을
한 줄로 설명하라(§5.2 가 그 근거다).

**④ 상태 → 화면 처리 (실측 순서 그대로)**

```
between-tests → live → between-tests → live → … → between-tests → ended
```

- **`onopen` 직후 첫 상태는 거의 항상 `between-tests`** 다(프레임보다 먼저 온다).
  그 구간이 **최대 15초**일 수 있다(이슈 1 — run 이 큐에 있는 동안). 스켈레톤이 아니라
  "다음 테스트 준비 중" 계열 오버레이가 맞다.
- `between-tests` 실측 길이는 **0.1초 ~ 2.5초**(테스트 경계) — 짧은 깜빡임을 견디는
  최소 표시 시간(예: 300ms)을 두는 편이 낫다. **같은 상태를 두 번 보내지 않으므로**
  디바운스는 화면 쪽 책임이다.
- **`ended` 뒤 약 1.5초 후 `close(1000, "run finished")`** 가 온다.
  `code === 1000` 은 **정상**이다 — 오류로 분류해 캔버스를 지우면 안 된다.
  **마지막 프레임을 유지하고 그 위에 `runStatus` 배지를 덮어라**(§2.3 의 픽셀 샘플링이 근거).
- `{t:"error", code:"CDP_ATTACH_FAILED"}` 가 오면 **라이브 화면은 끝까지 없지만 실행은
  계속된다.** 그 문구(한국어)를 그대로 보여 주면 된다. 실행 실패로 표시하지 마라.

**⑤ close code 분류**

| code | 뜻 | 화면 |
|---|---|---|
| **1000** | 정상 종료(실행 끝) | 마지막 프레임 유지 + 배지 |
| **4401** | 토큰 불일치/부재/만료 | "접속 권한이 없습니다" — 재발급 후 1회 재시도는 가능 |
| **4404** | 스트림 세션 없음(이미 끝났거나 15초 내 시작 안 됨) | "라이브 화면을 열 수 없습니다" + 증적/영상으로 유도 |

★ **`onopen` 이 떠도 안심하지 마라** — 4401/4404 는 **핸드셰이크 성공 후 close** 로 온다
(04-gen-7 규약 그대로). `onclose.code` 를 반드시 본다.

**⑥ 녹화 실행(`sourceType === "steps"`)에는 라이브가 없다.**
`liveStreams` 는 코드 경로에만 배선했다. `RunDetail.sourceType` 으로 갈라라.

### 그 밖의 전달사항

7. **`RUNNER_WS_LIVE_PUBLIC_URL`** 이 녹화의 `RUNNER_WS_PUBLIC_URL` 과 **별도 변수**다
   (녹화 값에는 `/rec` 경로가 들어 있다). nginx `location /live/` 를 README 에 넣어 뒀다.
8. **프레임 크기는 1280×800 고정**이다(`use.viewport` 와 같은 값). 캔버스를 그 비율로 잡아라 —
   시안의 `aspect-ratio 16/10` 과 맞는다.
9. **docker 모드가 기본이다.** 개발 머신에서 코드 시나리오를 돌리려면
   `Dockerfile.code-exec` 를 빌드하거나 `RUNNER_CODE_EXECUTION_MODE=local` 을 명시해야 한다.
   안 하면 실행이 `error` + 한국어 안내로 거부된다 — Gen-Phase 6 의 통합검증 준비에 필요하다.
10. **WSL 에서 docker 모드를 쓰려면 `RUNNER_CODE_WORKSPACE_ROOT` 가 필수다**(§1.5a).
    안 넣으면 실행이 `error` + "이 경로는 Docker Desktop 에 마운트할 수 없습니다" 로 거부된다.
11. **console/network 로그는 여전히 수집하지 않는다**(04-gen-3 전달 6번 그대로).
    CDP 로 붙어도 **"붙기 전"의 로그는 못 받는다** — 부착까지 실측 1.3~2.6초가 걸린다.
    화면에 "코드 실행은 콘솔/네트워크 로그를 남기지 않습니다"를 명시하라.
12. **docker 모드에서 대상 사이트가 호스트 로컬이면** `baseUrl` 에 `host.docker.internal` 을
    써야 한다. 실행 다이얼로그의 안내문에 넣을 값이다(라운드 1 규약과 같다).
13. **`.g4` 검증 하네스는 커밋하지 않았다**(`apps/runner/node_modules/.g4/`).
    재측정이 필요하면 이 문서의 §2 조건과 `poc/r2/r2.ts` 를 참고해 다시 만들면 된다.
    측정 결과 원본은 [`r2-live-measurements.json`](./r2-live-measurements.json) 에 있다.
